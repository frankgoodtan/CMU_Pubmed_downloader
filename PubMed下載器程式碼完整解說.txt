為什麼要這樣寫、彼此怎麼串起來。內容會分好幾個階段陸續寫進這個檔案（用

這個檔案獨立放在桌面，跟專案資料夾完全無關，不會影響到任何程式碼。

--------------------------------------------------------------
1-1. 這個擴充功能在解決什麼問題？
--------------------------------------------------------------

情境：中國醫藥大學（CMU）的研究人員手上有一份 Excel，裡面列了幾百到上千篇
PubMed（美國國家醫學圖書館的論文資料庫）的論文。學校圖書館訂閱了很多出版社
的期刊，透過一個叫「EZproxy」的代理伺服器，登入後就能看到全文 PDF——但如果
要一篇一篇手動點「登入 → 搜尋 → 找全文連結 → 下載」，幾百篇要點到天荒地老。

這個 Chrome 擴充功能做的事，就是把這整套手動流程自動化：
  讀 Excel → 逐篇找到 PubMed 頁面 → 找出版社全文連結 → 判斷是哪家出版社
  → 用那家出版社專屬的手法把 PDF 抓下來 → 存檔 → 把結果寫回 Excel。

聽起來像是「寫一個迴圈跑過去就好」，但實際上很不簡單，因為：
  - 不同出版社的網頁結構天差地遠（Elsevier 一種做法、Wiley 又是另一種），
    直接抓網址常常抓到假 PDF（其實是 HTML 錯誤頁）。
  - 出版社會用 Cloudflare 之類的服務擋機器人，你抓太快、抓太像機器人，
    會被要求「證明你是人類」（勾 checkbox、選圖片這種驗證）。
  - 一次跑好幾篇效率才夠，但太多個同時打同一個網站又更容易被封。
  - 網路本來就不穩，某一篇卡住不能拖累其他篇。
  - 使用者中途可能要暫停、電腦可能會睡眠、瀏覽器擴充功能本身也有生命週期
    限制（後面會解釋）。

這份文件接下來會照著「資料怎麼流過整個系統」的順序，把每一塊怎麼處理這些
麻煩事講給你聽。

1-2. 先補幾個 Chrome 擴充功能的基本知識
--------------------------------------------------------------

如果你完全沒寫過 Chrome 擴充功能，這幾個名詞會一直出現，先講清楚：

●「Manifest V3（MV3）」
  Chrome 擴充功能的「規格版本」。你可以把 manifest.json 想成是這個擴充
  功能的「身分證+說明書」：它是誰、需要什麼權限（能不能碰下載、能不能碰
  cookie、能不能跟 checkbox 分頁互動...）、主程式入口在哪裡。

●「Service Worker（背景服務執行緒）」
  這是整個擴充功能的「大腦」，對應到這個專案的 src/background.js。
  它不是一個一直開著的視窗，而是瀏覽器背景默默跑的一段程式——沒有畫面，
  你看不到它，但它負責所有「真正做事」的邏輯：開分頁、判斷頁面內容、
  下載檔案、跟 Excel 互動...等等。

  這裡有個很重要、很多新手會踩到的坑：Chrome 為了省資源，MV3 的
  Service Worker **不是永遠活著的**。如果它閒置（沒有任何 Chrome API
  呼叫在跑）超過 30 秒，Chrome 會把它「終止」掉，等下次有訊息進來
  （例如使用者點了什麼、分頁有新事件）才會重新啟動一個全新的、記憶體
  歸零的 Service Worker。這代表：如果你在 Service Worker 的記憶體裡存了
  一堆變數（例如「現在跑到第幾篇」），這個 Service Worker 被砍掉重開後，
  這些變數會全部消失，除非你有另外存到 chrome.storage（一個瀏覽器提供、
  跨重啟都不會消失的儲存空間）裡。

  這個專案的因應方式：background.js 裡有個「keepalive」機制（第 119-141
  行附近），下載進行中每 20 秒呼叫一次很輕量的 Chrome API
  （chrome.runtime.getPlatformInfo），這個呼叫本身會讓 Chrome 重新計算
  「閒置 30 秒」這個倒數計時，只要這個呼叫沒斷過，Service Worker 就會
  一直被續命下去，不會被砍掉。之後會講到，這件事跟「為什麼 Discord
  通知有時候會漏掉」也有關係。

●「Native Messaging（原生訊息傳遞）」
  Chrome 擴充功能本身活在瀏覽器的「沙盒」裡，基於安全考量，**不能**
  直接操控你電腦的滑鼠、不能存取瀏覽器下載資料夾以外的檔案系統路徑、
  不能執行任意程式。但這個專案有兩個功能非做不可：
    (a) 偵測到人機驗證時，把滑鼠真的移到 checkbox 附近提醒使用者
        （這需要操控作業系統層級的滑鼠游標，瀏覽器沙盒內辦不到）
    (b) 「本地資料夾模式」：把 PDF 存到使用者自己選的任意資料夾
        （不是 Chrome 預設下載資料夾），這也超出瀏覽器沙盒的能力範圍。

  Native Messaging 就是 Chrome 官方提供的「合法後門」：擴充功能可以
  透過這個機制去啟動、跟電腦上一支「原生」（native，非瀏覽器沙盒限制）
  程式溝通——這個專案裡就是 native_host/python_write_love.py（處理滑鼠
  提醒）跟 native_host/python_file_manager.py（處理本地資料夾存檔）
  這兩支 Python 程式。使用者需要先手動「安裝」這兩個 native host
  （一鍵安裝.bat 做的事），把它們登記進 Windows 登錄檔／設定檔，Chrome
  才知道「這個擴充功能可以叫這支程式」。

  溝通的協定很陽春：Chrome 會把這支 Python 程式當一個子行程（process）
  啟動，透過標準輸入輸出（stdin/stdout）傳資料——訊息格式是「4 bytes
  的小端序整數（代表訊息長度）+ 那麼多 bytes 的 UTF-8 JSON 文字」。
  階段 6 會細講這部分的程式碼。

●「Message Passing（訊息傳遞）」
  Service Worker（background.js）沒有畫面，使用者看到、操作的視窗
  是 popup.js + popup.html（雖然叫 popup，但這個專案裡它是開成一個
  獨立小視窗，不是傳統那種點擴充功能圖示才彈出來、一點旁邊就關掉的
  迷你 popup）。這兩塊——background.js 跟 popup.js——是兩個完全獨立、
  互相看不到對方變數的執行環境，唯一溝通方式是靠 Chrome 提供的
  chrome.runtime.sendMessage() / chrome.runtime.onMessage 這組 API
  互相「喊話」：一邊送一個帶著 action 欄位（代表「這是什麼事件」）的
  物件，另一邊監聽、依 action 判斷要做什麼。階段 9 會細講。

1-4. 最高層次視角：一篇論文的完整旅程
--------------------------------------------------------------

在深入細節之前，先看一次「一篇論文從 Excel 裡的一列資料，變成硬碟裡一個
PDF 檔案」，中間依序經過哪些步驟、哪些檔案負責哪一段：

  1. 使用者在 popup.js 的介面上傳 Excel、按下「開始下載」
     → popup.js 透過 chrome.runtime.sendMessage() 把這個「開始」事件
       連同設定（並行數量、要不要保守模式...）送給 background.js

  2. background.js 收到訊息，用 xlsx.full.min.js 把 Excel 解析成一筆一筆
     的資料物件（PMID、標題、DOI...），塞進一個佇列（queue）

  3. background.js 開出設定好數量的「worker」（每個 worker 對應一個隱藏的
     瀏覽器分頁，tabId != null 但 active:false，使用者看不到它），每個
     worker 各自從佇列裡拿一筆資料開始處理——這部分是階段 2 的主題

  4. 單一 worker 拿到一筆資料後：
       a. 先確認 EZproxy 有沒有登入（階段 3）
       b. 導航到這篇論文的 PubMed 頁面（用 PMID 直達，或搜尋標題）
       c. 從 PubMed 頁面上找「Full Text」連結，判斷這個連結指向哪個出版商
          （full_text_platforms.js，階段 4）
       d. 依判斷結果，用那個出版商專屬的手法去抓真正的 PDF 網址／內容
       e. 過程中如果遇到人機驗證，暫停這個 worker、開一個讓使用者看得到
          的分頁、呼叫 python_write_love.py 提醒使用者手動處理（階段 5+6）
       f. 抓到 PDF 後，存檔——存到 Chrome 預設下載資料夾，或如果開了
          「本地資料夾模式」，改叫 python_file_manager.py 存到使用者
          自選的資料夾（階段 7）
       g. 把這一篇的結果（成功/失敗/待重試）寫回進度，即時同步一份到
          chrome.storage，每處理完 5 篇或使用者按暫停/停止時，把整份
          進度寫回 Excel 檔案本身

  5. 全部處理完（或使用者中途停止），把總結果統計，並且如果開了 Discord
     通知，發一則總結訊息到 Discord（階段 8）

  6. 整個過程中，background.js 會不斷用 chrome.runtime.sendMessage() 把
     即時進度、log 訊息送給 popup.js，popup.js 收到後更新畫面上的文字，
     讓使用者知道現在跑到哪、成功幾篇、失敗幾篇（階段 9）

這就是整個系統的骨架。接下來每個階段，會挑其中一段，把程式碼實際長什麼
樣子、為什麼要這樣設計、踩過什麼坑，講得更深入。

階段 2：下載引擎核心（Tab Pool 並行架構、worker 派發、佇列設計）
========================================================================

這階段的主角是 background.js 裡的這幾個函式：
  startDownloadEngine()、buildTabPool()、launchWorker()、runWorker()、
  checkStalledWorkers()、recycleWorkerTab()
以及貫穿全部函式的那個全域狀態物件 G（resetState() 定義它長什麼樣）。

--------------------------------------------------------------
2-1. 先講 G：整個下載引擎的「共用記事本」
--------------------------------------------------------------

JavaScript 沒有像其他語言那種「物件導向、每個 class 各自管理自己的狀態」
的強制規範，這個專案的做法很直接：整個 background.js 共用一個巨大的全域
變數 G（在檔案第 164 行：`let G = resetState();`），resetState() 回傳一個
物件，裡面塞滿了這次下載任務需要追蹤的所有東西：

  G.running / G.paused / G.stopped   —— 這次任務目前是什麼狀態
  G.targets                          —— 從 Excel 解析出來的完整論文清單
  G.queue                            —— 「還沒被任何 worker 認領」的索引佇列
  G.workers                          —— 每個 worker 現在在做什麼（給 UI 顯示用）
  G.ok / G.fail / G.skip / G.done    —— 統計數字
  G.tabPool                          —— 每個 worker 對應的隱藏分頁 tabId
  G.domainLocks                      —— 「哪個出版商現在被哪個 worker 佔用」
  G.activeWorkers / G.liveWorkerPromises —— 追蹤現在有幾個 worker 真的在跑

為什麼要這樣做，而不是把這些狀態包進一個 class？主要是因為 Service
Worker 本身沒有「多個實例」的概念——同一時間就是一份程式碼在跑，不需要
處理「兩個下載任務同時存在」這種情況，用一個全域物件反而簡單直接，所有
函式互相呼叫時不用一直傳參數傳來傳去。壞處是：任何函式都可以直接改到
G 的任何欄位，程式碼讀起來要花點心力才能抓到「這個函式到底動了哪些
狀態」——這也是為什麼你會看到很多函式旁邊有大段中文註解在解釋「這個
欄位是幹嘛的、為什麼要在這裡改它」，這其實是在補「全域狀態被到處改」
這件事天生比較難讀的缺點。

要注意：resetState() 回傳的這份初始值，只有在「使用者按下重設」或
Service Worker 剛啟動時才會套用一次。前面階段 1 提過 Service Worker
可能被 Chrome 中途砍掉重開——重開後這行 `let G = resetState()` 會重新
執行一次，G 裡原本記著的「跑到第幾篇、成功幾篇」全部歸零！這是這個
專案目前一個已知但沒處理的限制（我們在别的討論裡有聊過：如果真的中途
被砍，使用者會很明顯地感覺到「整批下載莫名停住」，不是靜悄悄地壞掉，
所以優先度沒有拉到最高，但這是你理解這份程式碼時值得記住的一個「地雷
還在那裡」）。

--------------------------------------------------------------
2-2. 為什麼要開好幾個「隱藏分頁」同時跑？── Tab Pool 的設計
--------------------------------------------------------------

如果只用一個分頁，一篇一篇處理，速度太慢——但這不是「開越多分頁越快」
這麼單純的問題，因為：
  - 出版社網站看到同一個 IP 短時間內開一大堆連線，容易被判定成機器人
  - 每個分頁都要真的載入網頁、跑 JavaScript，太多個同時跑，電腦資源
    也吃不消

所以這個專案的做法是：使用者在 popup 選一個「並行數量」（1/2/3/5 篇
同時跑），background.js 就開對應數量的**隱藏分頁**（buildTabPool()，
第 779-788 行）——注意 `active: false`，這代表分頁確實存在、確實在
背景載入網頁，但使用者在瀏覽器介面上看不到它、不會被它打擾。這些分頁
的 tabId 存進 G.tabPool 這個陣列，每個「worker」（下面會解釋 worker
是什麼）固定認領其中一個分頁反覆重複使用，不是每篇論文都開一個新分頁——
開新分頁本身有成本（要等頁面初始化），重複用同一個分頁、只是換網址
導航過去，效率好很多。

有個小地方值得注意：分頁用久了（同一個分頁重複導航很多次）有時候會
變慢，所以有個 WORKER_TAB_RECYCLE_EVERY 常數（目前設 15），worker
每處理滿 15 篇，會呼叫 recycleWorkerTab()（第 871-880 行）把舊分頁關掉、
開一個全新的分頁頂替——這是很典型的「與其花力氣去查為什麼分頁變慢，
不如乾脆定期換新的」這種工程上的務實解法。

--------------------------------------------------------------
2-3. Worker 是什麼？佇列怎麼運作？
--------------------------------------------------------------

「worker」在這個專案裡不是什麼特殊的瀏覽器 API（跟 Web Worker 那個
概念沒關係，只是借用同一個詞彙），單純是「一個會一直重複執行
runWorker() 這個迴圈的非同步函式」。可以想像成：你僱用了 N 個工讀生
（N=並行數量），每個工讀生手上有一份共用的待辦清單（G.queue），大家
輪流去清單上面撕一張紙條下來做，做完了、有空了，再撕下一張，一直到
清單撕光為止。

實際程式碼（runWorker()，第 883 行開始）長這樣的邏輯迴圈：

  while (true) {
    // 1. 如果整個任務被暫停了，這裡卡住等待，直到恢復
    while (G.paused && !G.stopped) await sleep(500);
    if (G.stopped) break;                       // 任務被停止，結束這個 worker

    // 2. 如果現在有 cookie 清理／人機驗證在跑，等它結束
    while (G.cookieCleanupRequested && !G.stopped) await waitForCookieCleanup(workerIdx);
    await waitForManualVerification(workerIdx);

    if (G.queue.length === 0) break;             // 清單撕光了，這個 worker 收工

    // 3. 從清單「拿一張紙條」——G.queue.shift() 拿佇列最前面那個索引
    const idx = G.queue.shift();
    const item = G.targets[idx];

    // 4. 處理這一篇（呼叫 getPdfUrlWithFallback 等一整套流程，這是階段4的主題）
    ...

    // 5. 更新統計、寫 log、視情況休息一下（保守模式）
    ...
  }

這裡的 G.queue.shift() 是整個並行機制的核心：因為 JavaScript 的
Service Worker 是**單執行緒**的（同一時間只有一段程式碼真的在跑，不會
有兩個 worker「同時」執行 shift() 導致搶到同一篇的問題——這跟其他語言
「多執行緒需要加鎖才安全」的情況不一樣，JS 的 async/await 是「協作式」
的，執行到 await 才會讓出控制權給別的工作繼續跑，shift() 這種單一行
的同步操作不會被打斷），所以不需要額外寫鎖定機制，每個 worker 各自跑
自己的 while 迴圈，靠著佇列自然而然地不會拿到同一篇。

--------------------------------------------------------------
2-4. 彈性 Worker 池：某一篇卡住了怎麼辦？
--------------------------------------------------------------

如果只是固定開 N 個 worker、佇列跑完就結束，會有個問題：萬一某個
worker 卡在某一篇很久（例如那個出版社網站特別慢、或者剛好搭配一個
需要重試很多次的頁面），這個 worker 就沒辦法去處理佇列裡剩下的其他
篇，整體並行數量實質上掉到 N-1，拖慢速度。

這個專案的解法是「彈性 worker 池」（checkStalledWorkers()，第 833-869
行）：background.js 開一個計時器（每 STALL_CHECK_INTERVAL_MS＝5 秒
巡視一次），檢查每個 worker「處理目前這篇」花了多久，超過
STALL_THRESHOLD_MS（一般模式 40 秒、保守模式拉長到 100 秒——保守模式
本來速度就故意放慢，門檻也要跟著放寬，不然正常的慢速下載會被誤判成
卡住）就判定「這個 worker 卡住了」，做兩件事：
  1. 標記它「這篇做完就收工」（G.workerRetireFlags），不是立刻中斷它
     手上正在做的事（半路打斷可能讓那篇的狀態變得很奇怪，例如 Excel
     寫到一半），而是讓它自然做完這一篇再結束。
  2. 立刻另外開一個新 worker（launchWorker(..., {needsTab:true})）去
     接手佇列，維持整體並行數。

但這裡也要小心「無限增生」的風險：如果是系統性問題（例如網路整段斷
掉），每一篇都會卡住，若沒有上限，就會不斷開新 worker，開到電腦資源
耗盡。所以有 STALL_MAX_TOTAL_WORKERS（同時存在的 worker 總數上限）擋
著，超過上限就不再開新的，只在 log 裡警告一次（不會每 5 秒都刷一次
警告訊息洗版，用 G.stallCapWarned 記錄「上次警告是什麼時候」，超過
60 秒才會再警告一次）。

--------------------------------------------------------------
2-5. Domain Lock：為什麼同時間不能有兩個 worker 打同一家出版社？
--------------------------------------------------------------

Tab Pool 讓好幾篇「同時」在處理，但如果剛好兩篇都是 Elsevier 的論文，
兩個 worker「同時」對 Elsevier 的網站發出請求，被出版社的反爬蟲機制
判定為可疑行為的風險會提高很多（正常人類不會同時從同一台電腦對同一個
網站開好幾個連線做同樣的事）。

acquireDomainLock() / releaseDomainLock()（第 2430-2456 行附近）就是
處理這件事：每次要真正對某個出版商網域發出下載請求前，先用
getPublisherLockKey() 把網址「歸類」成一個固定的出版商代號（例如
sciencedirect.com、linkinghub-elsevier-com 這些網域都歸類成
"elsevier"），然後檢查 G.domainLocks 這個物件裡這個代號現在是不是被
別的 worker 佔用著——如果是，就等待（每 800ms 檢查一次，等到鎖被釋放
或任務被停止），拿到鎖才繼續做事，做完呼叫 releaseDomainLock() 放掉。

這其實就是程式教科書裡「互斥鎖（mutex）」的概念，只是這裡沒有用什麼
特殊的鎖定 API，就是一個普通物件 + 一個「輪詢等待」的迴圈，因為前面
提過 JS 是單執行緒協作式的，這樣寫已經足夠安全，不需要更複雜的機制。

--------------------------------------------------------------
2-6. 保守模式：故意讓自己「看起來像人類」
--------------------------------------------------------------

除了並行數量本身受控，這個專案還故意在每篇之間、每一批之間加上延遲：

  getInterItemDelayMs()（第 5099 行）：
    保守模式：8-15 秒（8000 + 隨機 0-7000 毫秒）
    一般模式：2-4 秒
    每個 worker 處理完一篇、要拿下一篇之前都會 sleep 這麼久。

  每完成 25 篇（G.done % 25 === 0），保守模式下額外休息 1-2 分鐘
    （runWorker() 第 1272-1276 行）。

這些數字都用 Math.random() 加了隨機範圍，不是固定死的秒數——真人操作
電腦本來就不會每次間隔剛好一模一樣，固定的間隔反而是機器人的特徵之一，
加隨機性是刻意讓行為模式更像人類、降低被出版社風控系統盯上的機率。

--------------------------------------------------------------
2-7. 整個引擎啟動的順序（串起來看一次）
--------------------------------------------------------------

startDownloadEngine()（第 716-777 行）是整個下載流程真正的起點，順序是：

  1. startKeepAlive()——開始前面階段1提過的 Service Worker 續命機制
  2. 檢查 EZproxy 有沒有登入，沒有就跳出登入表單等使用者輸入（階段3細講）
  3. buildTabPool(G.concurrent)——開好對應並行數量的隱藏分頁
  4. 用一個 for 迴圈呼叫 launchWorker(i)，一次啟動 G.concurrent 個 worker，
     每個都各自開始跑自己的 runWorker() 迴圈
  5. 開 checkStalledWorkers 的巡視計時器
  6. `await Promise.race(G.liveWorkerPromises)` 這一段是「一直等到所有
     worker 都結束」的寫法：G.liveWorkerPromises 是一個 Set，裝著每個
     還在跑的 worker 的 Promise，只要這個 Set 還有東西，就繼續等；
     每個 worker 結束時會把自己的 Promise 從這個 Set 移除（launchWorker()
     裡的 finally 區塊），所以這個 while 迴圈會一直跑到「所有 worker
     都主動把自己移除」才真正跳出。
  7. 全部結束後呼叫 finishAll()，做收尾工作（統計總結、寫最終 Excel、
     發 Discord 總結通知...）

高深的多執行緒技巧，是「開好幾個隱藏分頁 + 一個共用佇列 + 大家各自跑
迴圈去搶佇列」這種相對樸素、但很務實的設計，外加卡住偵測、出版商鎖、
故意放慢速度這幾層額外的穩定性/安全性考量。

階段 3：EZproxy 登入與 Cookie 管理
========================================================================

這階段的主角：checkLogin()、ensureLogin()、requestLogin()、isLoginPage()
（登入相關），以及 clearNonCmuProxyCookies()、shouldRemoveCookie()、
requestCookieCleanup()、waitForCookieCleanup()（cookie 清理相關）。

--------------------------------------------------------------
3-1. EZproxy 是什麼、為什麼會卡在這裡
--------------------------------------------------------------

大學圖書館訂閱的期刊資料庫，出版社認證的方式通常是「看你的網路 IP 是不是
學校校園網路範圍內」——校內電腦直接連上去就有權限，家裡或校外電腦連上去
會被擋。EZproxy 是一種很常見的解決方案：它是一台伺服器，你先登入
EZproxy（用學校帳密），之後所有網址都改成「經過 EZproxy 轉一手」的形式，
EZproxy 會用學校的名義去跟出版社要資料，出版社看到的是「這個請求來自
學校 IP」，就會放行——不管你人真的在校內還是在家裡。

這個專案裡看到的 `pubmed-ncbi-nlm-nih-gov.autorpa.cmu.edu.tw:8443` 這種
奇怪網址，就是 EZproxy 的轉址格式：原本的網域 `pubmed.ncbi.nlm.nih.gov`
被改寫成「把每個 `.` 換成 `-`，再接上 `.autorpa.cmu.edu.tw:8443`」，
這樣瀏覽器看起來是連到 autorpa.cmu.edu.tw 這個網域（EZproxy 主機），
但內容其實是它去 pubmed.ncbi.nlm.nih.gov 抓回來、轉發給你的。

程式碼裡這幾個常數就是在定義這套轉換規則（background.js 第 86-90 行）：
  EZPROXY_BASE  = "autorpa.cmu.edu.tw:8443"
  PUBMED_EZPROXY = "https://pubmed-ncbi-nlm-nih-gov." + EZPROXY_BASE
  LOGIN_URL      = 學校登入頁網址

之後你會在 chinese_paper_search.js 看到同樣的轉換規則被用在 CNKI（中國
知網）身上（toEzproxyCnkiUrl 這類函式），概念完全一樣，只是套用在不同
的目標網域。

--------------------------------------------------------------
3-2. 登入流程：三層函式分工
--------------------------------------------------------------

●  checkLogin(tabId)（第 2521 行）
   最單純：導航到 PubMed 首頁，看網址最後停在哪裡——如果停在
   `/user/login` 或 `/proxy/login` 這類網址，代表沒登入；如果順利停在
   `pubmed-ncbi-nlm-nih-gov.autorpa.cmu.edu.tw` 這種轉址過的網域，代表
   已登入。只回傳 true/false，不處理任何登入動作本身。這個函式只在
   startDownloadEngine() 一開始呼叫一次，確認「這整批任務開始前」有沒有
   登入。

●  isLoginPage(tabId)（第 2587 行）
   跟 checkLogin 目的不同：checkLogin 是「主動去問有沒有登入」，
   isLoginPage 是「看現在這個分頁『剛好』停在哪裡，是不是登入頁」——用在
   下載過程中，某個 worker 導航到某個網址後，發現意外被導回登入頁（例如
   session 過期了），要能夠偵測到這件事並觸發重新登入。

●  ensureLogin(tabId)（第 2543 行）
   這是登入流程真正被各個 worker 呼叫的入口，設計上要處理一個微妙的
   併發問題：**如果同時有好幾個 worker 都發現自己需要登入，不能每個都
   各自跳出一次登入表單**（使用者會被連續彈好幾次要求輸入帳密，非常
   困惑，而且其中幾次會因為 session 已經被別的 worker 登入成功而變成
   多餘的）。

   解法是一個簡單的鎖（G.loginLock）加等待隊列（G.loginWaiters）：
     - 第一個發現需要登入的 worker，把 G.loginLock 設成 true，自己去跳
       登入表單（呼叫 requestLogin()）。
     - 這之後才發現自己也需要登入的其他 worker，看到 G.loginLock 是
       true，不會自己再跳一次表單，而是把自己的「resolve 函式」塞進
       G.loginWaiters 這個陣列，然後停在那裡等（`await new Promise(...)`
       這種寫法，重點是這個 Promise 不會自己 resolve，要等別人主動呼叫
       它才會繼續）。
     - 真正在處理登入的那個 worker，不管成功失敗，最後都會在 finally
       區塊裡把 G.loginWaiters 裡所有等待中的 resolve 函式都呼叫一次
       （`G.loginWaiters.splice(0).forEach(resolve => resolve())`），
       釋放所有原本卡住的 worker，讓它們繼續往下跑（如果登入失敗，
       G.stopped 會被設成 true，這些被釋放的 worker 下一輪迴圈檢查到
       G.stopped 就會自然結束，不會誤以為登入成功繼續亂跑）。

   這是很典型的「一個人做事、其他人排隊等結果」模式，你可能聽過的專有
   名詞是 "single-flight"（多個請求合併成一次實際執行）。

●  requestLogin(tabId)（第 2640 行）
   真正跳出表單、等使用者輸入、把帳密填進網頁欄位、送出的地方。這裡有
   幾個值得注意的細節：

   - 驗證碼圖片的擷取（captureLoginCaptcha()，第 2611 行）：登入頁的
     驗證碼是一張圖片（`<img id="captcha_img">`），但圖片網址常常是
     blob URL（瀏覽器記憶體裡的暫存資料，不是一般網址，其他地方沒辦法
     直接用這個網址取得圖片內容），所以要用 fetch() 把圖片內容抓下來、
     轉成 base64 編碼的文字（fetchImgBase64()，第 2734 行），這樣才能
     透過 chrome.runtime.sendMessage() 把圖片內容送給 popup.js 顯示
     出來給使用者看。base64 是「把任意二進位資料編碼成純文字」的
     標準做法，圖片、聲音等資料常常這樣傳遞。

   - 填表單的方式很講究（第 2664-2705 行）：不是單純寫
     `input.value = "帳號"` 就結束，而是先透過
     `Object.getOwnPropertyDescriptor(...).set` 拿到瀏覽器原生的
     「設定 input value」這個 setter 函式直接呼叫，再手動觸發 input/
     change 事件。這是因為現代網頁（尤其用 React/Vue 這類框架寫的）
     常常會攔截、覆寫 input 元素的 value setter 來做自己的資料綁定，
     如果你透過一般的 `el.value = x` 賦值，框架可能偵測不到「這個值被
     改了」，畫面看起來有填但實際上網頁內部的狀態沒有真的更新，送出
     表單時後端收到空值。直接呼叫瀏覽器原生 setter、再手動觸發事件，
     是繞過框架攔截、確保「網頁真的認為這個欄位被改過」的標準技巧。

   - 重試機制：帳密或驗證碼可能打錯，MAX_LOGIN_ATTEMPTS 設成 3，每次
     失敗都重新擷取一張新的驗證碼圖片再讓使用者重試，而不是直接判定
     整批任務失敗——連續失敗滿 3 次才真的放棄。

--------------------------------------------------------------
3-3. 為什麼需要清 Cookie？── Cookie 是什麼、為什麼會累積成問題
--------------------------------------------------------------

先講一下 Cookie 的基本概念（如果你已經懂可以跳過這段）：Cookie 是網站
存在你瀏覽器裡的一小段文字資料，網站可以用它記住「你是誰」（登入狀態）、
「你做過什麼」（追蹤分析）等等。每次瀏覽器對這個網站發出請求，都會自動
把屬於這個網站的所有 Cookie 一起附在請求的 HTTP header 裡送過去。

問題來了：這個擴充功能一次要連續處理幾百篇論文，經過幾十個不同出版社
的網站，每個網站都會在你的瀏覽器裡累積自己的 Cookie（登入狀態的、
Google Analytics 這類分析追蹤用的、Cloudflare 這類反爬蟲驗證通過紀錄
的...），累積久了會出現兩個實際問題：

  1. **HTTP header 過大**：Cookie 是跟著每次請求一起送的，累積太多
     Cookie，整個請求的 header 大小可能超過伺服器能接受的上限，
     伺服器會直接回一個錯誤（常見錯誤訊息是「request header too
     large」），導致原本應該正常的請求失敗。

  2. **舊的追蹤/分析 Cookie 干擾判斷**：某些網站的機器人偵測邏輯，會
     去看你的 Cookie 歷史「像不像正常瀏覽行為」，累積太多、太密集的
     Cookie 活動記錄，反而更容易被判定成異常。

但清 Cookie 不能「整批全清光」——這樣會把 EZproxy 的登入狀態、
Cloudflare 驗證通過的紀錄也一起清掉，逼你重新登入、重新過一次驗證，
反而更麻煩。所以這裡有一整套「該留哪些、該清哪些」的判斷邏輯。

--------------------------------------------------------------
3-4. Cookie 該留該清的判斷邏輯
--------------------------------------------------------------

shouldRemoveCookie(cookie, mode)（第 2955 行）是核心判斷函式，先看幾個
「一定要保留」的規則（不管什麼模式都適用）：

  isChallengeClearanceCookie()：cf_clearance、cf_chl 開頭、__cf_bm 這些
    名字的 Cookie，是 Cloudflare「你已經證明是人類」的通行證，清掉的話
    所有網站都要重新跳一次人機驗證，絕對不能清。

  isChallengeProtectedDomain()：sciencedirectassets.com 這個網域（放
    ScienceDirect 實際 PDF 檔案的地方）也是用類似機制擋機器人，同樣要
    保留。

  isCmuProxyCookieDomain() + isLikelyCmuSessionCookie()：EZproxy 本身
    的登入 session（sid、lid、fcsid 這幾個 Cookie 名稱），這個沒了就要
    重新登入 EZproxy。注意這裡特別排除了「出版商 proxy 子網域」
    （像 onlinelibrary-wiley-com.autorpa.cmu.edu.tw 這種），只保護
    「真正的」EZproxy 根網域——這個區分是因為 EZproxy 轉址後每個出版商
    會各自有一個子網域，這些子網域的 Cookie 不是「登入狀態」，是各
    出版商自己的追蹤/session Cookie，不需要特別保護。

除了這些「永遠保留」的規則，還分兩種清理力道（mode 參數）：

  mode = "routine"（例行排程清理）：
    只清 isTrackingCookieName() 判定為「純追蹤用」的 Cookie——Google
    Analytics（_ga 開頭）、Facebook Pixel（_fbp）、Adobe（amcv、mbox）
    這類名稱，這些清掉完全不影響任何登入或驗證狀態，只是清掉「這個
    使用者被追蹤紀錄了什麼」的資料，很安全，可以常態性清。

  mode = "header-too-large"（真的遇到請求失敗才觸發）：
    比較積極：除了明確判斷像是登入/授權/session/token 名稱的 Cookie
    （isLikelyAuthOrSessionCookieName()，例如名字裡有 session、auth、
    token、license、shib、saml 這些關鍵字）繼續保留，其餘 Cookie 全部
    清掉——因為都已經真的出現錯誤了，代表溫和清法不夠，要更積極處理
    才能解決問題，這時候情願冒一點「可能要重新過一次某個網站驗證」的
    風險，換取請求能夠成功。

--------------------------------------------------------------
3-5. 清理的時機點：為什麼要等「所有 worker 都閒置」
--------------------------------------------------------------

清 Cookie 這個動作本身很快，但**什麼時候**去清很重要：如果 worker A
正在下載一半（例如正在等某個出版社網站回應），這時候 worker B 觸發了
Cookie 清理，把 A 依賴的某個 session Cookie 清掉了，A 手上進行到一半的
請求可能會突然失敗或行為異常。

所以這裡設計成「排程制」，不是「誰發現問題就誰立刻清」：

  requestCookieCleanup(reason)（第 3057 行）：任何 worker 發現需要清
    Cookie 時，呼叫這個函式，只是把 G.cookieCleanupRequested 設成
    true、記下原因——不會立刻清。

  waitForCookieCleanup(workerIdx)（第 3026 行）：每個 worker 在自己的
    主迴圈裡，每次要拿下一篇之前都會呼叫這個函式檢查——如果
    G.cookieCleanupRequested 是 true，這個 worker 就先卡在這裡等
    （`await sleep(500)` 一直檢查），直到符合這兩個條件才會有人真的
    動手清理：
      (a) 目前沒有其他 worker 正在清理中（G.cookieCleanupInProgress）
      (b) **目前活躍中的 worker 數量是 0**（G.activeWorkers === 0）——
          意思是所有 worker 都恰好處理完手上那一篇、正卡在「要拿下一篇
          之前」這個檢查點，沒有任何 worker 正在半路上做事。

    這樣設計確保 Cookie 清理發生的當下，絕對不會有任何 worker 正卡在
    一個依賴著即將被清掉的 Cookie 的請求中途——這是一種「安全點」
    （safe point）的概念，跟資料庫或程式語言的垃圾回收機制常用的
    「等所有執行緒都走到某個安全點才做全域性的操作」是同一種思路。

  清理完成後，把所有旗標歸零、G.cookieCleanupEpoch 加 1（這個計數器
  的用途：某些呼叫端會記下「我開始等待時 epoch 是多少」，之後比較
  現在的 epoch 有沒有變大，藉此判斷「清理是不是真的發生過一次了」，
  用來決定某篇論文要不要因為清理而重新整篇重跑）——所有 worker 才會
  繼續各自的迴圈。

--------------------------------------------------------------
3-6. 兩個實際觸發清理的時機
--------------------------------------------------------------

  1. 例行排程：runWorker() 裡每完成 G.cookieCleanupEvery（預設 10）篇，
     呼叫一次 requestCookieCleanup()，用溫和的 "routine" 模式清追蹤
     Cookie，防患未然。

  2. 真的出錯才觸發：requestCookieCleanupIfHeaderTooLarge()（第 3084
     行）在偵測到頁面真的顯示了「request header too large」這類錯誤
     文字時呼叫，用積極的 "header-too-large" 模式清理，同時標記這篇
     需要整個重新開始（cookieCleanupShouldRestartItem()）。

     這裡有個很細節、但很能看出「這套系統是被真實踩坑養出來的」的例子：
     程式碼裡特別排除了 CNKI（中國知網）網域——因為 CNKI 用的
     Tomcat 伺服器，不管是什麼原因，出錯都一律顯示同一種通用的
     「HTTP Status 400 – Bad Request」錯誤頁，如果用寬鬆的字串比對
     （只要頁面出現「400」+「Bad Request」就觸發），會被 CNKI 這種
     跟 header 大小完全無關的錯誤誤觸發，害整批任務不必要地暫停去清
     Cookie（清了也沒用，因為問題根本不是 Cookie 太多，而後果還會
     提早清掉 CNKI 自己還在用、還沒累積到真的需要重建的 session）。
     所以在 CNKI 網域上，只認「request header is too large」這句真正
     精確的錯誤訊息，不吃寬鬆比對——這種「先出過事、才加上的特殊排除」
     在這個專案的註解裡到處都是，讀程式碼的時候留意這種註解，往往
     就是在告訴你「這裡曾經真的出過什麼包」。

需要登入時怎麼避免重複彈出表單、以及 Cookie 清理為什麼要分「清什麼」
（追蹤用的可以隨便清，登入/驗證用的要保護）跟「什麼時候清」（一定要

========================================================================
階段 4：PDF 抓取邏輯
========================================================================

這是整個專案最「雜」的一塊——因為每個出版商的網站長相都不一樣，需要
各自的應對方式。主角是 src/platform_handlers/full_text_platforms.js
（1097 行，就是為了裝這些出版商各自的邏輯而獨立拆出來的檔案），加上
background.js 裡負責「下載前先確認抓到的真的是 PDF」跟「遇到反爬蟲
挑戰先想辦法解開」的幾個函式。

--------------------------------------------------------------
4-1. 為什麼需要一張「平台判斷表」，而不是寫一串 if/else？
--------------------------------------------------------------

full_text_platforms.js 開頭的註解，直接講了這個檔案存在的理由，這是
一個很好的真實案例，值得整段搬過來看：這個檔案是為了取代「原本散在
background.js 三個地方、各自為政的平台判斷邏輯」——原本的寫法是：
在 PubMed 頁面上找連結時判斷一次是哪個平台，真正要下載前又重新判斷
一次，各家的 getPdf 函式內部可能又各自再猜一次，三個地方各寫各的、
標準還不一致（有的只看網址字串、有的還看連結上的標籤文字）。

這種寫法會導致什麼問題？程式碼裡直接舉了一個真實發生過的 bug：Oxford
Academic 這個出版社用的是「Silverchair」這套系統（JAMA 也是用同一套
系統），PubMed 頁面上，這個連結旁邊的說明文字明明白白寫著「See full
text options at Silverchair Information Systems」，但因為當初 JAMA/
Silverchair 那一段判斷邏輯只檢查網址字串裡有沒有 "jamanetwork" 或
"silverchair" 這幾個字，沒有去看這段「標籤文字」，Oxford Academic 的
網址剛好不含這些字，於是判斷邏輯漏接了它，掉進去「萬用兜底」處理，
兜底邏輯又對這個網址套用了不適用的猜測規則（後面會講的 Atypon 平台
猜測法），猜出來的三個候選網址全部 404。

解法就是把這一大坨判斷邏輯，收斂成**一張表**——FULL_TEXT_PLATFORMS
（第 42 行開始）——這是一個很值得學起來的設計模式，正式名稱通常叫
「查找表／分派表（dispatch table）」：把「一堆條件分支各自對應不同
處理方式」這種邏輯，統一寫成一個陣列，每個元素描述一種情況該怎麼
判斷、怎麼處理，陣列元素的**順序**就代表判斷的優先順序，要新增一種
情況時，只要在陣列裡加一個新元素，不用去每個角落找哪裡還有一份沒改到
的判斷邏輯（程式碼開頭的「新增一個出版商平台的步驟」那段註解，就是
在講這件事：新增平台只需要在這張表裡加一項，pollForFullTextLink 跟
getPdfFromFullTextOption 兩處呼叫端都會自動吃到新的一項，不必再改）。

表裡每個平台項目長這樣（以 jama 為例）：

  {
    id: "jama",
    pickLabel: "JAMA / Silverchair",
    pickSelectors: [ ...在 PubMed 頁面上找這個平台專屬連結用的 CSS 選擇器... ],
    match: ft => ft.source === "jama" ||
      /silverchair/i.test(ft.label || "") ||       // ← 修掉那個 bug 的地方：同時看標籤文字
      /jamanetwork|silverchair/i.test(ft.url || ""),
    getPdf: getPdfFromJama,
  }

match() 的註解特別強調「務必同時檢查 source / label / url 三者，不要
只看網址」——這正是從那次踩坑學到的教訓，直接寫進了程式碼的設計規範裡。

--------------------------------------------------------------
4-2. 找連結、判斷平台、真正抓 PDF：三個步驟怎麼串起來
--------------------------------------------------------------

  1. pollForFullTextLink(tabId, maxMs)（第 167 行）
     在 PubMed 文章頁上，每 500 毫秒重新掃一次頁面（PubMed 的全文連結
     常常是非同步載入出來的，不是頁面一開始就有），依序用每個平台的
     pickSelectors 去找連結，找不到專屬 picker 命中的（包含 Wiley——
     它沒有專屬 picker，一律先被萬用兜底 selector 抓到，標成
     source="generic"，等真正判斷平台時才會被表格裡 wiley 項目的
     match() 重新歸類），最後才找 CMU Library 的連結（這種連結是
     圖書館自家系統轉介，不是真正的出版社全文，一律視為不可用）。

  2. getPdfFromFullTextOption(tabId, ft)（第 215 行）
     真正要下載前呼叫，邏輯只有一行：`FULL_TEXT_PLATFORMS.find(p =>
     p.match(ft))`——在表裡找第一個 match() 回傳 true 的平台，把處理
     權交給它的 getPdf() 函式。因為 generic 那個項目的 match 永遠回傳
     true 且放在陣列最後一個，這行程式碼**保證**一定會找到一個平台可用
     （不會發生「找不到符合的平台」這種情況）。

  3. 各平台各自的 getPdf(tabId, url) 函式
     這裡才是真正「認識這個出版商網站」的地方，隨便舉幾個真實技巧：

     ● citation_pdf_url 這個 meta 標籤（getPdfFromGenericPage 第 785-798
       行）：很多學術網站會在網頁 `<head>` 裡放一個
       `<meta name="citation_pdf_url" content="...">`，這是 Google
       Scholar 制定的一套「學術網頁 metadata」慣例（讓 Google Scholar
       這類服務能自動找到論文的 PDF 網址），很多出版社網站沿用了這個
       標籤。程式碼優先看這個標籤，因為它是「伺服器端直接告訴你答案」，
       比起在頁面上東找西找連結、或是用網址規律去猜，準確度高很多。
       這裡也有個踩坑記錄：這個規則對 Silverchair 平台（Oxford
       Academic、JAMA）常常誤判，因為這類網站的文章網址路徑本身就帶
       著 "/doi/" 這幾個字，容易被誤認成另一套系統（Atypon）的網址
       規律，所以程式碼特別把「檢查 meta 標籤」排在「硬猜網址規律」
       之前，確保有 meta 標籤可用時優先相信它。

     ● buildPdfCandidatesFromUrl：對於用 Atypon 系統的出版社（SAGE、
       Liebert 等，網址通常帶 DOI），這個函式會用同一個 DOI 组出好幾個
       可能的 PDF 網址變體（/doi/pdf/、/doi/pdfdirect/、/doi/epdf/），
       因為不同版本的網站設定可能只有其中一種變體真的有效，全部準備好，
       之後一個一個嘗試（見下面 4-4）。

     ● pdf.js viewer 讀取（readPdfJsViewerUrl，getPdfFromGenericPage
       第 817-826 行）：有些網站是用瀏覽器內建/第三方的 pdf.js 元件
       直接把 PDF「畫」在網頁裡當作一個檢視器顯示，頁面上根本沒有任何
       `<a href="....pdf">` 這種連結可以抓，PDF 檔案網址被藏在
       JavaScript 執行環境裡的一個變數（PDFViewerApplication）裡。這種
       情況要用 chrome.scripting.executeScript 注入程式碼去讀那個
       JavaScript 變數的值，才拿得到真正的檔案網址。

     ● LWW（Wolters Kluwer）的特殊欄位（第 839-846 行）：PDF 連結不是
       一般的 `<a>` 標籤，而是掛在頁面某個容器元素的 `data-pdf-url`
       這個自訂屬性上，要用 `.getAttribute("data-pdf-url")` 才能讀到。

     這些細節你不需要每個都背起來，重點是體會這件事：**同一個「找到
     PDF 網址」的目標，在不同網站上實現方式可以天差地遠**——這正是為
     什麼這個檔案要獨立拆分、而且會長到 1097 行的原因。

--------------------------------------------------------------
4-3. 抓到網址不代表就是真的 PDF：預檢機制
--------------------------------------------------------------

即使照著上面的邏輯抓到了一個「看起來像 PDF 網址」的網址，直接拿去下載
存檔是有風險的：很多出版社在你沒有權限、或觸發了反爬蟲機制時，那個
網址回傳的其實是一個 HTML 錯誤頁（例如「您沒有訂閱權限」、或是
Cloudflare 的人機驗證頁），如果沒有先確認內容，程式會把這個 HTML 錯誤
頁存成一個叫 XXX.pdf 的檔案——**這是最麻煩的一種失敗**，因為 Excel
上會顯示「下載成功」，實際上那個檔案打開來是垃圾，使用者可能事後才會
發現，而且要花更多力氣去分辨哪些是真的成功、哪些是假成功。

preflightPdfCheck(url, diag)（第 4086 行）就是用來擋這件事：在真正觸發
下載之前，先用 fetch() 只抓網址開頭的一小段內容（用 HTTP 的 Range
header，`"Range": "bytes=0-2047"`，只跟伺服器要前 2KB，不用真的把整個
檔案下載兩次，省頻寬也省時間），檢查：
  - HTTP 狀態碼是不是 200（成功）
  - content-type header 是不是 application/pdf
  - 內容開頭是不是 "%PDF"（這是所有 PDF 檔案的標準檔頭識別字串，
    不管 content-type 有沒有騙人，真正的 PDF 二進位內容一定以這四個
    字元開頭）
  - 如果都不是 PDF，內容看起來像不像人機驗證頁（用階段 5 會細講的
    isManualVerificationText() 判斷）

回傳值有三種：true（確定是 PDF）、false（確定不是）、null（沒辦法
判斷，例如網路逾時，這時候選擇「照常放行去嘗試」而不是直接判定失敗——
寧可多花時間試一次真的下載，也不要因為預檢本身的問題就錯殺一篇原本
抓得到的論文）。

--------------------------------------------------------------
4-4. 抓到的候選網址不只一個：容錯的候選清單機制
--------------------------------------------------------------

上面提到 buildPdfCandidatesFromUrl 會針對同一篇文章組出好幾個可能的
PDF 網址變體，正式版本呼叫的 normalizePdfCandidates()（第 4038 行）
會把「平台 getPdf() 回傳的候選」、「URL 變體」、「備用來源」全部整理
成一份去重過的清單（用一個 Set 記錄已經看過的網址，避免重複嘗試同一個
網址）。

runWorker() 裡（階段 2 看過的那段迴圈）拿到這份候選清單後，用一個
for 迴圈依序嘗試（background.js 約第 986-1015 行）：第一個候選失敗，
就換下一個，一直試到成功或全部試完——這是很典型的「容錯重試」設計：
與其花力氣把「猜出正確網址」這件事做到 100% 準確（對這麼多不同出版社
網站來說近乎不可能），不如準備好幾個「有機會是對的」候選，一個一個
實際去試，最終的成功率反而更高、更省心。

--------------------------------------------------------------
4-5. 遇到反爬蟲挑戰：warmup 機制
--------------------------------------------------------------

有些網站（特別是 PMC 跟 ScienceDirect/Elsevier）的 PDF 網址本身，就是
被反爬蟲機制保護著的：你直接對這個網址發請求（不管是用 fetch() 還是
chrome.downloads.download()），一定會先拿到一個「請證明你是真人瀏覽器」
的挑戰頁，不會是真正的檔案內容。urlNeedsChallengeWarmup()（第 4209
行）就是列出「已知這種行為的網站」清單。

warmUpAntiBotChallenge()（第 4290 行，這也是這次對話前段我們一起改過
的函式）處理的邏輯是：既然直接打那個網址一定會先卡關，那就先讓一個
**真正的瀏覽器分頁**去導航到那個網址（或是它的文章頁——PDF 端點本身
往往連瀏覽器分頁都直接導航進去也解不開挑戰，要先去文章頁把挑戰跑過
一次，設好通行的 Cookie，之後同一個 PDF 端點才會真的放行），因為
Cloudflare 這類挑戰機制設計上就是要區分「這是不是一個會執行 JavaScript
的真實瀏覽器」，用真正的分頁導航過去，把它的 JavaScript 挑戰跑完，
是唯一能真正解開的辦法——fetch() 或直接發送下載請求都不會執行網頁裡的
JavaScript，永遠解不開這種挑戰。

跑完挑戰、拿到通行 Cookie 之後，再重新對同一個網址做一次
preflightPdfCheck()——如果這次真的變成 PDF 了，代表挑戰解開了，可以
繼續正常下載流程；如果解不開、或者判斷出這是需要**真人**手動處理的
人機驗證（不是自動就能跑過去的那種），就會進入階段 5 要講的「暫停、
提醒使用者手動處理」流程。

【階段 4 結束】
========================================================================

這階段看完，你應該理解「抓 PDF」這件事在這個專案裡拆成好幾層：先用
一張分派表判斷「這是哪個出版商」、各平台各自的手法去找出候選網址、
組出好幾個候選變體來容錯、下載前先做內容預檢確保真的是 PDF（不是
騙人的 HTML 錯誤頁）、遇到反爬蟲挑戰時先用真實分頁「暖身」把挑戰解開。
這幾層疊在一起，就是為什麼同一個「抓 PDF」的動作，程式碼要寫這麼多、
這麼細——每一層都是為了應付現實世界裡各種不配合的網站。

========================================================================
階段 5：人機驗證偵測與 Native Host 溝通
========================================================================

這階段就是這次對話前半段我們一起花很多力氣修過的那部分：background.js
怎麼判斷「現在卡在人機驗證頁」、怎麼在畫面上定位驗證元件、怎麼透過
Native Messaging 叫 Python 幫忙提醒使用者。主角：
requestManualVerificationPause()、monitorManualVerification()、
tabShowsManualVerification()、location_target.js 的
locateAllTargetElements()、triggerVerificationHeart()。

--------------------------------------------------------------
5-1. 什麼是人機驗證、為什麼躲不掉
--------------------------------------------------------------

出版社網站用 Cloudflare（或 reCAPTCHA、hCaptcha 之類服務）擋機器人，
判定「這個連線可疑」時，會插入一個「請證明你是人類」的頁面——可能是
勾一個 checkbox（Cloudflare Turnstile 最常見的形式）、選圖片、或單純
一個會自動偵測滑鼠移動軌跡的隱形挑戰。這個專案的設計哲學很明確（在
python_write_love.py 開頭寫得很清楚）：**遇到這種頁面，不去想辦法自動
突破它**（自動幫使用者點掉 checkbox 這種行為，一來技術上很難穩定做到，
二來這正是反爬蟲機制想抓的行為模式，容易弄巧成拙、讓帳號被判定更可疑），
而是暫停下載、把畫面切到這個驗證頁、想辦法「提醒」使用者自己去手動
處理，處理完再繼續。

所以這整個系統要解決三個問題：
  1. 怎麼判斷「現在卡在驗證頁」（偵測）
  2. 怎麼讓使用者的注意力被導到正確的地方（提醒——這就是那個會畫框、
     移動滑鼠的 native host 在做的事）
  3. 怎麼知道「使用者處理完了，可以繼續」（自動偵測驗證通過）

--------------------------------------------------------------
5-2. 偵測「這是不是驗證頁」：曾經三套邏輯各自為政
--------------------------------------------------------------

在這次對話之前，background.js 裡其實有三處各自獨立判斷「這是不是驗證
頁」的地方，各有各的選擇器清單、各有各的判斷邏輯，這正是我們這次修的
一大塊。三處分別是：

  ● checkPageState()：判斷 PubMed 文章頁本身是不是 bot 頁
  ● tabShowsManualVerification()：判斷出版商頁面（ScienceDirect 等）
    是不是卡在驗證頁——這個結果直接決定要不要觸發整套暫停＋提醒流程
  ● locateAllTargetElements()（location_target.js）：實際去抓候選
    元件的螢幕座標，供 native host 定位用

這三處原本各用各的一套 CSS 選擇器去找頁面上的驗證元件，其中一個很致命
的問題是：**沒有任何一處會穿透 shadow root**。這裡要先解釋一下 shadow
DOM 是什麼：一般網頁的 `document.querySelectorAll()` 這種查詢方式，
只會在「一般的 DOM 樹」裡找，但現代網頁元件（尤其像 Cloudflare
Turnstile 這種第三方嵌入元件）常常會把自己真正的內容包在一個叫
「shadow root」的封裝結構裡——這是瀏覽器提供的一種「元件內部細節不
外洩」的封裝機制（跟程式語言裡「私有變數」的概念有點像），刻意設計成
一般的 querySelectorAll 查詢**穿不進去**，除非你明確知道要用
`.shadowRoot` 這個屬性再往下鑽一層。

Cloudflare Turnstile 很常把實際渲染出的 iframe/容器包在這種 shadow
root 裡再插進頁面，這代表：只用一般的 querySelectorAll 查詢，會直接
漏掉真正的驗證元件——程式判斷「這裡沒有偵測到已知驗證元件」，但實際上
畫面上真的卡著一個驗證挑戰，使用者眼睛看得到，程式卻「視而不見」。

這次的修法：在會查詢頁面 DOM 的地方，改用一個遞迴函式（deepQuerySelectorAll，
location_target.js 裡最早寫好、後來被複製套用到另外兩處），邏輯很簡單：
先查目前這層，再對每個「有 shadowRoot 屬性」的節點，往下鑽進它的
shadow root 裡用同一套選擇器再查一次，結果合併起來——這樣不管驗證元件
藏在幾層 shadow root 裡都找得到。

--------------------------------------------------------------
5-3. 螢幕座標怎麼算出來的：DOM 座標 → 螢幕絕對座標
--------------------------------------------------------------

找到驗證元件在網頁裡的位置後，還有一段路要走：网頁裡量到的座標
（`getBoundingClientRect()`）是「相對於瀏覽器分頁可視區域（viewport）
左上角」的座標，但要讓 Python 那邊的 native host 真的把 OS 滑鼠移過去，
需要的是「相對於整個電腦螢幕左上角」的絕對座標——這中間差了：瀏覽器
視窗本身在螢幕上的位置、瀏覽器視窗自己的標題列/工具列佔用的高度、還有
螢幕的 DPI 縮放比例（Windows 常見的 125%、150% 顯示設定）。

location_target.js 的 rectToScreenPoint()（第 49 行附近）負責把這一整
串換算做掉：
  1. 用 chrome.windows.get() 拿瀏覽器視窗本身在螢幕上的外框位置
  2. 假設左右留白對稱、上方留白全部是瀏覽器 UI（分頁列、網址列）佔掉的
     高度，算出「網頁可視區域左上角」對應到螢幕上的哪個座標
  3. 把网頁裡量到的元件座標加上這個偏移量
  4. **最後**才乘上 devicePixelRatio（DPI 縮放比例），轉成螢幕的「實體
     像素」座標——程式碼裡特別強調這個乘法要放在最後一步做，不能在
     中間任何一步提早乘，不然 CSS 像素跟實體像素這兩種不同單位的數字
     混在一起加減，算出來的結果會是錯的。

這種「單位換算的乘法要擺在正確的步驟」，是很多座標/幾何計算 bug 的
常見來源，值得記住這個原則：**先確定每個中間變數的單位是什麼、全程
保持單位一致，只在最後真正要交給下一層系統時才做單位轉換**。

--------------------------------------------------------------
5-4. 暫停與排隊：requestManualVerificationPause 那一整套
--------------------------------------------------------------

判斷出「卡住了、需要人工處理」之後，流程進到 requestManualVerificationPause()：

  - 把 G.verifyPending 設成 true——這是一個全域旗標，runWorker() 主
    迴圈每一輪都會呼叫 waitForManualVerification()（見階段2的迴圈）
    去檢查它，是 true 就整個 worker 卡住等待，不去拿下一篇——這樣就
    達到「暫停派發新任務」的效果，不需要真的去中斷任何 worker 正在
    做的事，是一種很輕量的「大家看旗標自己決定要不要繼續跑」的協調
    方式。
  - 把出問題的分頁切到前景（chrome.tabs.update({active:true})），讓
    使用者看得到、能夠互動。
  - 如果同時有好幾個 worker 都撞到驗證頁（例如兩個 worker 剛好都在
    處理同一家出版社的論文），不會互相搶畫面：只有第一筆會立刻顯示，
    其餘的排進 G.verifyQueue 這個佇列裡，等第一筆處理完
    （finishManualVerification()）才依序顯示下一筆——這確保畫面上
    永遠只有一個驗證頁在跟使用者互動，不會同時彈出好幾個讓人不知道
    先處理哪個。

--------------------------------------------------------------
5-5. 三階段重試協定：monitorManualVerification
--------------------------------------------------------------

驗證頁顯示出來之後，這個函式（background.js）負責背景監看「使用者
是不是已經處理完了」，同時主動觸發 native host 提醒使用者。設計成
三個階段：

  階段 A（先等）：驗證挑戰元件幾乎都是非同步載入的（先轉圈圈讀取幾秒
    才真的渲染出 checkbox），太早去查 DOM 只會查到還沒撐開的空殼，
    所以先整整等 5 秒（VERIFY_INITIAL_LOAD_WAIT_MS），讓畫面穩定下來
    再開始。

  階段 B（判斷是不是真的需要驗證）：等完立刻查一次，如果驗證根本沒有
    真的出現過（例如純文字誤判、或分頁還停在空白頁），直接判定「不需要
    驗證」結束，不浪費任何嘗試次數。

  階段 C（最多 3 次嘗試）：每次嘗試都重新查一次全部候選驗證元件（畫面
    中途可能才渲染出新的候選——同一頁可能同時鋪了 reCAPTCHA 又鋪
    hCaptcha 當備援），依序處理每一個候選：把它的座標傳給 native
    host，等 native host 回應（畫完提醒框、確認關閉）才換下一個候選，
    避免好幾個 native host 進程同時搶滑鼠、疊出好幾個提醒視窗。全部
    候選都提醒過一次後，等 5 秒，檢查驗證是否已經通過：通過就結束；
    沒通過、還有嘗試次數，就調低比對門檻（VERIFY_ATTEMPT_THRESHOLDS，
    見階段6）進入下一次——原本因為門檻太嚴格被判定「沒中」、但實際上
    是對的候選，降低門檻後有機會被接受。

  3 次都沒過，判定逾時結束——但這不代表整個下載流程放棄：只是先把
  這筆驗證結束、解除全域暫停，讓其他排隊項目能繼續跑；這一篇本身會
  依照「驗證期間失敗不算數」的機制自動重跑最多 2 次（見 runWorker()
  裡的 shouldRestartAfterVerify 邏輯，階段2提過的 G.verifyEpoch 計數器
  就是用來判斷「這個 worker 開始處理這篇的當下，有沒有發生過一次完整
  的驗證流程」，發生過就把這篇重新排回佇列）。

--------------------------------------------------------------
5-6. 完全找不到候選元件時：window_region 盲搜
--------------------------------------------------------------

上面的偵測邏輯萬一還是完全找不到任何已知的驗證元件（可能是全新型態
的挑戰、選擇器沒涵蓋到、或元件真的還沒渲染出來），程式不會就此放棄，
而是退而求其次：把「目前分頁所在瀏覽器視窗」的整個螢幕範圍算出來（用
5-3 講的同一套座標換算公式，只是把「元件的 rect」換成「整個 viewport
本身」），傳給 native host，讓它把搜尋範圍收斂在「這個瀏覽器視窗裡」，
而不是完全放棄、或搜尋整個電腦螢幕（含其他視窗、桌面、工作列，誤判
率高很多，這正是這次對話中我們新增的一層，取代了原本「完全沒有候選
元件就直接放棄」的行為）。

--------------------------------------------------------------
5-7. 跟 Native Host 溝通的訊息長什麼樣
--------------------------------------------------------------

triggerVerificationHeart()（background.js）組出送給 python_write_love.py
的 payload，大概長這樣：

  {
    cmd: "draw_heart",
    contextLabel: "ScienceDirect / 出版社驗證頁",
    x, y, left, top, width, height,     // 有找到候選元件才會帶，DOM量出來的
                                          // 螢幕絕對座標外框
    matchedSelector: ".cf-turnstile",   // 是哪個 CSS 選擇器抓到的
    windowRegion: {...},                // 完全沒候選元件時才帶，瀏覽器視窗範圍
    domRegionMinScore, logoMinScore,    // 這輪嘗試用的比對門檻（會逐次調低）
    clearDebugFolder: true,             // 只有整個驗證流程第一次呼叫才帶
  }

值得特別提的一點：background.js 傳過去的 left/top/width/height，
**native host 那邊不會直接當作最終座標使用**——因為 checkbox 通常在
跨網域的 iframe 裡，網頁的 DOM 只看得到 iframe 這個外框元素本身，看
不進 iframe 裡面（這也是瀏覽器的安全機制，防止一個網頁能偷看另一個
網域嵌入內容的細節），所以 DOM 量到的座標只能拿來當「大概去這個範圍
裡找」的提示，checkbox 真正的精確位置，要靠 native host 自己對這個
範圍做圖像樣板比對才能定出來——這就是階段 6 的主題了。

background.js 呼叫 chrome.runtime.sendNativeMessage() 送出這個 payload
後，會傳一個 callback 函式，native host 那邊的 Python 程式做完事情、
真的把提醒視窗關掉之後，才會透過這個機制把 ack（回應）送回來，
background.js 的候選輪流迴圈是 `await` 這個 callback 才會處理下一個
候選——如果 ack 提早送出（提醒視窗還開著），下一個候選的螢幕掃描
很可能會撞上這個還沒關掉的視窗，把比對結果帶偏。這種「等對方真的做完
事、關掉視窗才回應」的協定設計，是為了確保多個候選依序處理時彼此
不會互相干擾。

階段 6：Native Host 內部原理（python_write_love.py，1402 行）
========================================================================

這支 Python 程式是這次對話花最多力氣一起除錯、重寫的地方，也是整個
專案裡跟「作業系統底層」牽涉最深的一塊。分四塊講：Native Messaging

--------------------------------------------------------------
6-1. Native Messaging 協定：4 bytes 長度 + JSON
--------------------------------------------------------------

階段 1 提過，Chrome 跟 native host 之間用「標準輸入輸出（stdin/
stdout）」傳資料，格式規定得很陽春（Chrome 官方規格）：每則訊息前面
先送 4 個 bytes，用「小端序（little-endian）」編碼成一個整數，代表
「接下來這則訊息的 JSON 文字有幾個 bytes」；讀的一方先讀這 4 bytes
算出長度，再照著這個長度去讀那麼多 bytes、當作 UTF-8 編碼的 JSON
文字解析。

  read_message()：
    raw_length = sys.stdin.buffer.read(4)
    length = struct.unpack("<I", raw_length)[0]   // "<I" = 小端序、4-byte 無號整數
    return json.loads(sys.stdin.buffer.read(length).decode("utf-8"))

  send_message()：
    data = json.dumps(payload).encode("utf-8")
    sys.stdout.buffer.write(struct.pack("<I", len(data)))   // 先送長度
    sys.stdout.buffer.write(data)                            // 再送內容

這種「先講清楚接下來有多長」的協定設計，叫做「長度前綴（length-
prefixed）」協定，是很多底層通訊協定共用的手法——好處是讀的一方永遠
知道「這則訊息什麼時候讀完」，不用去猜測 JSON 字串本身有沒有結束（比
起「用某個特殊字元當作訊息結尾」的做法更可靠，因為 JSON 內容本身就
可能包含各種字元，用特殊字元當結尾容易誤判）。

python_write_love.py 是「一次性」的 native host：Chrome 每次呼叫都會
啟動一個全新的 Python 行程（process），這個行程讀一則訊息、處理、回一則
訊息，就結束了（main() 函式最後執行完，整個程式退出）。這跟階段 7 會
講的另一個 native host（python_file_manager.py）不一樣——那個是常駐的，
一次啟動後透過一個持續開著的通道（Port）被連續呼叫很多次，這裡先記住
這個差異，階段 7 會解釋為什麼要用不同的模式。

--------------------------------------------------------------
6-2. ctypes：Python 怎麼直接呼叫 Windows 作業系統的底層函式
--------------------------------------------------------------

Python 標準函式庫本身沒有「移動滑鼠」、「取得螢幕解析度」這種功能——
這些是作業系統層級的能力。ctypes 是 Python 內建的一個模組，功能是
「讓 Python 程式碼可以直接呼叫用 C 語言寫的動態連結函式庫（DLL）」，
Windows 作業系統本身大量的底層功能，都是透過一套叫 Win32 API 的 C
語言函式庫（user32.dll、kernel32.dll 這些檔案）提供的。

程式碼開頭：
  USER32 = ctypes.windll.user32

這一行拿到的 USER32，就是「user32.dll 這個檔案」的 Python 端代理
物件，之後 `USER32.SetCursorPos(x, y)`、`USER32.GetSystemMetrics(0)`
這種寫法，實際上就是直接呼叫 Windows 系統裡 user32.dll 這個檔案裡的
對應函式——這已經不是「瀏覽器沙盒裡的 JavaScript」能做到的事了，這正是
階段 1 提過「為什麼一定要透過 Native Messaging 叫外部程式」的原因。

這份文件裡出現過的幾個關鍵 Win32 API 呼叫：

  ● SetCursorPos(x, y) / GetCursorPos()：設定/讀取滑鼠游標在螢幕上的
    絕對座標（實體像素）。這是「移動滑鼠」的核心呼叫，注意它只是把
    游標「傳送」到那個座標，不會產生任何點擊事件。

  ● GetSystemMetrics(0) / GetSystemMetrics(1)：讀取螢幕寬度／高度
    （這兩個數字對應到 Win32 定義的常數 SM_CXSCREEN=0、
    SM_CYSCREEN=1，程式碼裡直接寫數字 0/1，這是因為 ctypes 呼叫
    C 函式庫時通常不會另外去定義這些常數的 Python 名稱，直接查文件
    抄數字比較省事）。

  ● SetProcessDpiAwareness()（enable_windows_dpi_awareness()，第 77
    行）：告訴 Windows「這個程式自己會處理不同 DPI 縮放比例，不需要
    Windows 幫我自動縮放座標」。這件事非做不可的原因：Windows 125%、
    150% 這類顯示縮放設定，如果程式沒有宣告自己「DPI 感知」，
    Windows 會在背後偷偷把座標做一次縮放轉換，導致「螢幕截圖抓到的
    像素座標」跟「SetCursorPos 需要的座標」不是同一個座標系統，兩邊
    對不齊，滑鼠移動位置會跟樣板比對出來的位置對不上。

  ● ShowWindow() / SetWindowPos()：控制一個視窗（提醒框）要不要顯示、
    要不要「置頂（topmost，蓋在所有其他視窗最上面）」。這裡有個這次
    對話中修過的真實 bug 值得記錄：這支程式是 Chrome 在背景生出來的
    子行程，不是使用者當下操作中的前景程式，直接呼叫
    `SetWindowPos(hwnd, HWND_TOPMOST, ...)` 硬把自己設成置頂，在
    Windows 上會觸發一個叫「前景視窗鎖定（foreground lock）」的機制，
    容易把工作列卡住，直到使用者手動切換一次前景視窗（例如打開工作
    管理員）才會恢復。修法是用另一個 API：

  ● AttachThreadInput()：把兩個「執行緒」的輸入佇列接在一起，讓其中
    一個執行緒可以借用另一個執行緒的權限。這裡的做法是：先用
    GetForegroundWindow() 找出目前真正的前景視窗（應該是 Chrome，
    因為 background.js 已經先把它切到前景），用
    GetWindowThreadProcessId() 找出那個視窗所屬的執行緒 ID，跟自己
    這個 Python 程式的執行緒 ID 用 AttachThreadInput 接在一起，這樣
    這個 Python 程式暫時「借到」了 Chrome 的前景權限，這時候呼叫
    SetForegroundWindow()／SetWindowPos(TOPMOST) 就不會觸發鎖定機制，
    做完立刻呼叫 AttachThreadInput 把兩者分開，不留殘留狀態。這是
    很多背景小工具（提醒視窗、通知彈窗）用來可靠搶到前景/置頂、又
    不會把工作列卡住的標準做法。

--------------------------------------------------------------
6-3. OpenCV 樣板比對：電腦怎麼「看懂」畫面上的 checkbox
--------------------------------------------------------------

Python 這邊拿到的座標（background.js 傳來的 dom_region 或 window_
region）只是「大概去這個範圍找」的提示，真正要找出 checkbox 精確位置，
靠的是 OpenCV（cv2）這個電腦視覺函式庫做「樣板比對（template
matching）」——先準備好幾張「長什麼樣子」的參考圖片（native_host/
資料夾裡那些 .png、.jpg 檔案，例如 common_checkbox_template_
cloudflare.png），對截下來的螢幕畫面（capture_virtual_desktop()，用
mss 這個套件截圖）去搜尋「畫面裡哪一塊區域，看起來最像這張參考圖片」。

  find_best_match()（第 110 行）：核心比對邏輯是 cv2.matchTemplate()，
  這是 OpenCV 內建的函式，會把參考圖片當作一個小視窗，在整張截圖上
  滑動比對，每個位置都算出一個「相似度分數」，回傳分數最高的位置跟
  分數本身。

  為什麼要「多尺度」（multi-scale）：同一個 checkbox 元件，在不同
  網頁縮放比例、不同瀏覽器視窗大小下，畫面上呈現的實際像素尺寸會不
  一樣——參考圖片是固定大小的，直接拿去比對，遇到畫面上的元件比參考
  圖片大或小一點，比對分數會明顯下降，容易找不到或找錯。解法是把
  參考圖片依照一組縮放比例（min_scale=0.85 到 max_scale=1.15，切
  13 個階梯）各自縮放成不同尺寸，每個尺寸都比對一次，取分數最高的
  那個尺寸——這樣就能容忍畫面顯示比例上下 15% 左右的差異。

  三層由粗到細的比對策略（locate_target() 系列函式，這是階段 5 提過
  「background.js 傳來的座標只是範圍提示」的下游）：
    第 0 層：直接在 background.js 給的範圍裡比對 common_checkbox 樣板
      （空白方形 checkbox 的通用長相）。
    第 1 層：沒中就退而在同一範圍裡找「廠商 logo」（Cloudflare／
      reCAPTCHA／hCaptcha 各自的圖示，這些是廠商固定資產，不會因為
      頁面語言不同而改變，比含文字的整條驗證列穩定），找到 logo 後，
      用「logo 左上角到 checkbox 中心」這個事先量好的固定向量（乘上
      這次比對到的縮放比例），大概推算出 checkbox 可能在哪，再對那
      附近一小塊範圍做第二次精確比對。
    第 2 層（window_region 的情況）：範圍變成整個瀏覽器視窗，門檻拉
      高很多（範圍變大、假陽性風險也變高，要求分數要更有信心才採信）。

  這整套「先找大而穩定的特徵（logo）、再用相對位置去推算小而多變的
  目標（checkbox）」的策略，是電腦視覺裡常見的思路：越獨特、越不會
  跟畫面其他東西混淆的特徵，越適合當第一層定位依據；真正要的目標
  本身如果很小、很容易跟其他東西長得像（一個空白方框，畫面上哪裡都
  可能有類似的東西），直接搜尋整個螢幕誤判率會很高，先靠好認的特徵
  「大概定位」、縮小範圍後再精確找，準確度會好很多。

--------------------------------------------------------------
6-4. 真人滑鼠軌跡重播：這次對話改最多次的地方
--------------------------------------------------------------

找到目標座標後，要把滑鼠「移過去」——但如果直接 SetCursorPos(target_x,
target_y) 瞬間跳過去，看起來完全不像真人操作（真人移動滑鼠是有速度、
有一點自然抖動的連續過程）。這個專案的做法是：找一批事先錄好的「真人
實際移動滑鼠去點 checkbox」的軌跡資料（dev-tools/真人點擊資料收集/
mouse_recording/ 底下那個 JSON 檔案，100 筆真實錄製），從裡面挑資料
出來重播。

錄製資料怎麼存的（normalize_trial_trace()，把原始錄製轉換成一份可以
套用在「任何方向、任何距離」的通用格式）：

  對每一筆真人移動，量出起點到終點的直線距離（distance）跟總花費時間
  （durationMs），然後把錄製過程中每個取樣點，換算成兩個相對座標：
    u：這個點在「沿著移動方向」上，走了整趟距離的幾分之幾（0 到 1
       之間，也可能略超過 1，代表真人手部自然的「衝過頭再修正回來」）
    v：這個點「垂直偏離主軸方向」多遠，一樣用整趟距離的比例表示（有
       正有負，代表左右兩側的自然抖動）

  這樣一來，同一筆錄製資料，不管實際要套用在多長的距離、往哪個方向
  移動，都可以用「起點 + 方向向量 × 距離 × u（沿軸）+ 垂直方向向量 ×
  距離 × v（垂直）」這條公式，還原出對應方向/距離下的絕對座標。

  這次對話花最多時間處理的，是「怎麼正確使用這份資料」，中間踩過
  好幾個坑，值得完整記錄一次（這也是很好的「設計決策怎麼被使用者
  實測回饋一步步修正」的案例）：

  第一版（有問題）：挑一筆錄製資料，把它的 u/v 直接乘上「這次實際
    要移動的距離」，時間也整段用一個比例縮放去套用。問題：如果隨機
    挑到的那筆錄製資料，原本距離跟這次實際要移動的距離差很多（例如
    錄製時走了 500px，這次只要走 30px），把整段動作硬拉伸/壓縮，
    會產生極度不自然的抖動或死板的緩慢滑行——這正是使用者最早反映
    的「有時候很快有時候很慢」。

  第二版（片段擷取）：改成不縮放，直接使用某一段錄製資料「原始」的
    像素位移量跟時間間隔，只從頭開始擷取一小段（擷取到累積位移量
    大約等於這次剩餘距離就停），模板比剩餘距離長就只取一截、比剩餘
    距離短就整段播完再串接下一段繼續——但這裡又踩了兩個新坑：
      (a) 一開始擷取的是軌跡的「開頭」，但開頭其實是真人動作的起手/
          加速階段，不是「精準收斂到終點」的動作特徵，越接近目標、
          越常需要擷取短片段，就越常把好幾筆不同錄製「各自的起手」
          接在一起，看起來像終點附近一直重新起步、繞來繞去——改成
          擷取軌跡的「結尾」（真正代表「精準收斂」的那段真實動作）
          才對。
      (b) 擷取結尾時，如果沒有排除原始資料裡 u>1（衝過頭再修正）的
          點，這些點的位移量是照「模板完整距離」換算的，套在一個
          只剩一小段距離的情境下，換算出來的位移可能遠遠超過剩餘
          距離，滑鼠會直接衝過目標一大截才轉回來——修法是這種情況
          排除掉 u>1 的點。

  第三版（規模比對＋抖動按比例縮小）：就算修好上面兩點，量化測試
    還是發現：如果目標距離遠小於錄製資料庫裡最短的樣本規模（這批
    錄製資料全部至少 197px 起跳），不管挑哪一筆、截哪一段，v（垂直
    抖動）的絕對像素量天生都是照「長距離移動」的規模設計的，套用在
    很短的距離上，抖動幅度相對於這麼短的移動來說永遠顯得誇張——這
    是資料本身的規模限制，不是挑選/截取邏輯能解決的問題。最後的
    處理：
      - 挑模板時優先選「原始距離」跟這次剩餘距離規模相近的（不是
        純隨機，也不是強制要求非常接近，是在隨機性跟合適度之間取
        一個折衷的候選池）。
      - 目標距離明顯小於資料庫最短樣本時，額外把 v（只有垂直抖動，
        不影響沿主軸的真實位移量跟時間節奏）按比例縮小——距離越短，
        抖動幅度縮得越多，但留一個下限，不縮到完全變成死板的直線。

  這整個過程示範了一件事：**一個「聽起來很合理」的初版設計
  （「用真人資料就一定自然」），實際套進各種邊界情況（距離很近、很遠、
  資料庫規模跟需求對不上）測試後，常常會冒出設計時沒想到的問題**，
  透過量化指標（例如「實際走的路徑長度 ÷ 直線距離」這個比值，越接近
  1 代表越沒有繞路）加上實際視覺化觀察（下面 6-5 會提到那個畫紅點+
  倒數+黃色路徑的除錯工具），一步一步把問題定位出來、修正掉，比單靠
  「感覺」去猜問題出在哪裡有效率得多。

--------------------------------------------------------------
6-5. 提醒視窗：tkinter 疊圖
--------------------------------------------------------------

找到座標、滑鼠移過去之後，程式用 Python 內建的 tkinter 函式庫，開一個
小視窗疊在畫面上，畫出：
  - 藍色半透明框：background.js 用 DOM 量到的驗證元件外框
  - 紅色半透明框：Python 自己比對出來的 checkbox 精確範圍
  - 黃色小圓點：滑鼠實際移動去的目標點
  - 文字標籤：這個候選是哪個 CSS 選擇器抓到的、比對是靠哪一層成功的

這個視窗本身也修過一個這次對話中發現的問題：它疊在 checkbox 正上方
（整支工具的目的就是要標出這個位置），但原本是一般不透明視窗，會真的
擋住使用者想手動點擊的滑鼠事件——顯示的這幾秒內，使用者想點底下真正
的 checkbox，其實點到的是這個提醒視窗（它沒有接任何點擊事件，什麼都
不會發生），感覺就像滑鼠突然失靈。修法是加上 Windows 的
WS_EX_LAYERED | WS_EX_TRANSPARENT 這組視窗樣式旗標，讓這個視窗維持
正常顯示（看得到），但所有滑鼠事件全部「穿透」到底下真正的視窗——
視覺上還在、互動上卻不存在，這也是很多螢幕標註/提醒類工具常用的做法。

視窗畫完之後會等 MARKER_DISPLAY_MS（3 秒）自動關閉，關閉之後才透過
6-1 講的協定把 ack 回應送回 Chrome——這是階段 5 最後提過的那個「等
對方真的做完事才回應」的協定設計，在這裡具體實現的地方。

階段 7：Excel／本地資料夾模式／進度管理

--------------------------------------------------------------
7-1. 為什麼專案裡有兩套 Excel 函式庫？
--------------------------------------------------------------

src/ 底下同時存在 xlsx.full.min.js 跟 exceljs.bare.min.js 這兩個第三方
套件，都是「讀寫 Excel .xlsx 檔案」的函式庫，聽起來很多餘，但各自負責
不同任務：xlsx.full.min.js（SheetJS）主要在「解析使用者上傳的原始
Excel」這個場景用（popup.js 那邊），exceljs.bare.min.js 則是
background.js 裡幾乎所有「讀進度檔、改狀態欄、寫回去」的地方在用。會
挑 ExcelJS 做這件事，最主要的原因是：ExcelJS 對儲存格的「格式」
（字型顏色、填色）有比較完整的讀寫支援——階段 7-4 會講到，這個專案的
進度追蹤，很大一部分是靠儲存格的顏色去記錄狀態的，這需要一套能精細
控制格式的函式庫，不是隨便一套「把資料塞進表格」的套件都做得到。

--------------------------------------------------------------
7-2. 一般模式 vs 本地資料夾模式，為什麼要多開一個 native host？
--------------------------------------------------------------

前面幾個階段一直帶到「本地資料夾模式」這個詞，這裡完整解釋一次：

  一般模式：PDF 存到哪裡，是靠 Chrome 內建的 `chrome.downloads.
  download()` 這個 API，這個 API 有個天生的限制——filename 參數只能
  是「Chrome 預設下載資料夾底下的相對路徑」，沒辦法指定成使用者電腦上
  任意一個資料夾（例如 D 槽某個自訂路徑）。對大部分人來說這個限制不
  痛不癢，但如果使用者希望 PDF 直接存到指定的工作資料夾（而不是每次
  再從「下載」資料夾手動搬過去），這個 API 就做不到。

  本地資料夾模式：透過階段 6 提過的另一個 native host——
  python_file_manager.py——把檔案內容直接寫到使用者自選的任意資料夾，
  繞過 chrome.downloads.download() 的限制。這正是階段 1 提過「為什麼
  需要 Native Messaging」的第二個具體案例：擴充功能的沙盒限制辦不到的
  事，交給一支不受沙盒限制的原生程式代勞。

  這個 native host 的溝通模式，跟畫提醒框那支（python_write_love.py）
  刻意設計成不一樣：python_write_love.py 是「一次性」的——每次呼叫
  Chrome 都會生一個全新的行程，做完事就結束；python_file_manager.py
  則是**常駐**的——background.js 用 `chrome.runtime.connectNative()`
  開一條會持續開著的通道（Port），這支 Python 程式啟動一次後，主流程
  是一個 while 迴圈，持續讀取、處理一則又一則的訊息，直到 Chrome 把這
  條 Port 關掉（Python 這邊讀 stdin 讀到檔案結尾 EOF）才真正結束。為
  什麼要這樣設計？因為這支程式在「一次批次下載期間」會被連續呼叫非常
  多次（每篇存檔一次、每次進度更新一次、核對資料夾狀態一次...），
  如果每次呼叫都重新啟動一個全新的 Python 行程，啟動行程本身的開銷
  （尤其階段 6 提過，光是匯入 cv2、numpy 這些套件就可能要 0.5-2 秒）
  會被重複付出非常多次，累積起來很浪費；反過來，python_write_love.py
  一次驗證流程頂多呼叫個位數次，用完即丟反而更簡單、不用擔心「常駐
  行程萬一卡住怎麼辦」這種額外的複雜度。

  另外一個實作細節：Chrome 規定 native host「回傳給擴充功能」方向的
  單則訊息大小上限大約 1MB（擴充功能傳給 host 方向的上限高很多，不受
  這個限制）。python_file_manager.py 裡，讀取既有進度 Excel 檔案內容
  回傳給 background.js 這個情境，內容可能超過這個上限，所以有
  send_bytes_chunked()（第 60 行）這個函式，把資料切成一片一片（每片
  base64 編碼後大約 70 萬字元，留一點餘裕不逼近上限），依序送出多則
  訊息，JS 那邊收到後依照一個 id 把每片內容累加起來，直到收到帶著
  `done:true` 的最後一片，才算真的收完整。這是很典型的「大檔案分片
  傳輸」手法，遇到協定本身有訊息大小限制時常常要這樣處理。

--------------------------------------------------------------
7-3. 寫 Excel 這件事為什麼需要一個「排隊鎖」
--------------------------------------------------------------

_buildAndSaveExcel()（第 1603 行）是所有「真正把進度寫回 Excel」動作
的共用入口，但它自己不做事，只是把真正的工作 _buildAndSaveExcelImpl()
包進一個排隊機制：

  let _excelWriteLock = Promise.resolve();
  function _buildAndSaveExcel(opts) {
    const run = () => _buildAndSaveExcelImpl(opts);
    const result = _excelWriteLock.then(run, run);
    _excelWriteLock = result.catch(() => {});
    return result;
  }

這是一段很值得學起來的 JavaScript 寫法：`_excelWriteLock` 這個變數
永遠指向「最後一次排隊的工作」，每次呼叫 _buildAndSaveExcel()，新的
工作不是立刻執行，而是接在「目前排在隊伍最後的那個 Promise」後面
（`.then(run, run)`——不管前一個成功還是失敗都接著跑下一個），然後
把 `_excelWriteLock` 更新指向這個新工作，讓「下一次」呼叫接在這次
後面——這樣一串串接下去，就形成一個「先進先出」的隊伍，保證所有寫入
動作依照呼叫順序、一個一個依序執行，不會有兩個同時在跑。

為什麼需要這個？註解裡講得很清楚：真正的寫入動作是「先讀 storage 目前
內容 → 在記憶體裡修改 → 寫回 storage/磁碟」這種「讀-改-寫」的三步驟。
如果沒有排隊機制，兩個寫入動作剛好同時發生（例如下載進行中的例行寫入，
跟使用者手動觸發的「更新論文清單」剛好同時發生），兩邊會各自讀到
「對方寫入之前」的舊內容，各自算完各自寫回去，後寫完的那個會把先寫完
的那個整個蓋掉——這種問題在程式設計裡常被稱為「競態條件（race
condition）」，用一個排隊鎖把所有寫入動作序列化（一個接一個、不重疊）
執行，是解決這類問題最直接的辦法。你可能會好奇「JS 不是單執行緒嗎，
為什麼還會有競態條件？」——單執行緒保證的是「同一時刻只有一段程式碼
真的在跑」，但 `await` 讓出控制權的那一刻（例如等 storage 讀取、等
Excel 檔案處理完），另一段程式碼是可以插進來跑一段的，兩段「讀-改-寫」
交錯執行，還是會發生上面說的互相覆蓋問題——這正是 async/await 寫並行
程式碼時很容易忽略、但很重要的一個陷阱。

--------------------------------------------------------------
7-4. 用顏色記錄狀態：黃色高亮 vs 文字顏色，兩種不同的意義
--------------------------------------------------------------

_buildAndSaveExcelImpl()（第 1614 行）裡有個設計上的巧思：進度 Excel
的「下載狀況」這一欄，同時用了「儲存格填色（fill）」跟「文字顏色
（font color）」兩種視覺記號，分別代表兩件不同的事：

  文字顏色：代表這一列**目前**的狀態，是持續累積、不會被清掉的紀錄——
    黑色文字 = 下載成功、紅色文字 = 下載失敗、藍色文字 = 下次重試。
    不管跑第幾次、跑了多少輪，只要這一列還沒被重新處理過，文字顏色
    永遠反映著它最後一次被處理完的結果。

  黃色填色（背景）：代表「這一次執行有動過這一列」——每次
    _buildAndSaveExcelImpl() 開始寫入前，會先把整欄的填色全部清掉
    （`fill = NO_FILL`），再把這次真的處理過的列（G.resultsMap 裡有
    紀錄的）填上黃色。所以黃色只反映「最近這一次執行」動過哪些列，
    跟這些列的狀態是成功還是失敗完全無關——你可以想像成「螢光筆劃記
    這次做過的部分」，跟「這些部分的批改結果」是兩件事。

  這樣設計的好處：使用者重新開一次專案、接續之前的進度時，一眼就能
  分辨「這次剛跑完動了哪些列」跟「整體到目前為止累積下來的成功/失敗
  狀態」，不會混在一起。前面提過的 stripStatusHighlightB64()（第 1551
  行）就是在「接續舊專案、但這次還沒開始跑」的時候，先把上一輪留下的
  黃色高亮清掉（避免使用者一開啟就看到一堆「看起來像剛處理過」的黃色，
  誤以為這次已經跑過了），但文字顏色（真正的狀態）完全不動。

--------------------------------------------------------------
7-5. 斷點續傳：怎麼知道哪些已經下載過了
--------------------------------------------------------------

如果每次都要「跑過整份 Excel 五百篇、才知道哪些已經下載過」，效率
很差，而且假如中途 Chrome 重開過（階段 1 提過 Service Worker 記憶體會
歸零），G 裡面本來記著的東西也會不見。這個專案的做法：完成的 PMID
清單額外存一份到 `chrome.storage.local` 的 `completedPmids` 這個
欄位——storage 的資料**不會**因為 Service Worker 重開而消失（這是
storage 這個 API 存在的意義：提供一個「跨 Service Worker 生命週期」
都持續存在的地方）。

每次使用者按下「開始下載」，background.js 在 START_DOWNLOAD 這個訊息
處理裡（第 470 行附近），會先讀出這份 completedPmids，把使用者這次
要跑的目標清單（targets）裡，PMID 已經在這份清單中的項目直接過濾掉
（`targets.filter(t => !(t.pmid && doneSet.has(String(t.pmid))))`），
不會重複去下載已經成功過的論文——這就是「斷點續傳」的具體實作：不需要
記住「上次跑到第幾篇」這種順序性的進度，只需要記住「哪些 PMID 已經
確定成功了」這個集合，之後不管怎麼重新排序、不管中間發生什麼中斷，
只要拿這個集合去比對，就能自動跳過已完成的部分，剩下的自然就是還沒
做完的。

（這裡也呼應階段 2 結尾提過的那個限制：completedPmids 這種「最終
結果」有存進 storage、能夠撐過 Service Worker 重開，但 G.queue、
G.workers 這些「進行中的暫時性狀態」沒有——所以如果真的中途被砍掉，
損失的是「這一批還沒跑完的部分要重新開始派工」，不是「已經做完的
成果」，這是目前這個系統的斷點續傳只做到「篇級別」、還沒做到「整個
執行狀態都能無縫恢復」的原因。）

--------------------------------------------------------------
8-1. Discord 通知：webhook 是什麼、為什麼要重試
--------------------------------------------------------------

discord_notifier.js（173 行）負責的事很單純：組一段文字、送到 Discord。
背後用的機制叫「webhook」——這是很多服務（Discord、Slack 等）提供的
一種簡化整合方式：你不需要寫一整套「登入 Discord 帳號、呼叫完整 API」
的程式碼，只要對一個固定的網址（webhook URL，裡面已經包含了「這是哪個
Discord 頻道」的授權資訊）發一個 HTTP POST 請求，內容放你想發的訊息文字，
Discord 那邊就會自動把這則訊息貼到指定頻道——本質上就是一個很單純的
`fetch(webhookUrl, { method: "POST", body: JSON.stringify({content: 訊息文字}) })`。

通知的時機分兩種：
  - sendDiscordBatchUpdate()：每處理完 DISCORD_BATCH_SIZE（10）篇，發
    一次這一批各自的狀況＋累積進度。
  - sendDiscordFinalReport()：全部處理完（或使用者中途停止），發一次
    總結統計＋全部論文編號的精簡清單。

值得記錄的一段：discordWebhookPost() 這個真正發送的函式，原本是「打
一次、失敗就算了」——只把失敗原因寫進 thread log（不會顯示在主畫面），
完全沒有重試。這代表只要那一次 fetch() 剛好遇到網路瞬斷、或 Discord
那邊暫時性地回應太多請求（HTTP 429，「請求過於頻繁」的標準狀態碼），
那則通知就永久消失，使用者在主畫面上完全看不到任何「這則沒送出去」的
線索——這正是這次對話裡使用者反映「有時候收不到 Discord 通知」的真正
原因，不是 webhook 設定有問題。

修法（也是這次對話一起改的）：最多重試 2 次；如果 Discord 回應
HTTP 429，讀取回應內容裡帶的 retry_after 欄位（Discord 明確告訴你
「請等幾秒後再試」），照這個秒數等待再重送；伺服器端錯誤（5xx）用
固定短延遲重試；如果是其他 4xx（多半代表 webhook 網址本身失效或權限
問題，不是暫時性的，重試也不會變好），直接放棄不浪費時間；全部重試
用盡才真的放棄，這時額外呼叫 addLog()（不是只有 addThreadLog()），
讓使用者在主畫面上就看得到「⚠ Discord 通知發送失敗」，不用另外去翻
debug log 才知道發生過。這種「分辨清楚哪些錯誤該重試、哪些錯誤重試也
沒用」的思路，是設計任何網路請求重試機制時都該有的基本原則——盲目對
所有錯誤都重試，會讓「明顯壞掉、重試也沒用」的情況白白浪費時間；完全
不重試，又會把「單純運氣不好」的暫時性錯誤誤判成永久失敗。

--------------------------------------------------------------
8-2. 中文論文的特殊處境：為什麼 PubMed 標準流程對它們沒用
--------------------------------------------------------------

chinese_paper_search.js（420 行）處理一種特殊情況：PubMed 上收錄的
論文，如果原文是中文期刊，PubMed 資料庫裡的標題（Title 欄位）其實是
「英文翻譯」過的版本，而且慣例上會整段用「[ ]」中括號框住，用來標示
「這不是原文標題，是翻譯」。這種論文如果照著標準流程走（用這個英文
翻譯標題去出版社網站搜尋、或找 Full Text 連結），常常直接找不到全文
——因為出版社網站上根本不存在這個英文標題，論文的原文標題是中文。

判斷「這是不是中文期刊」的方式很直接：isBracketedChineseTitle()（第
78 行），只看標題整段是不是被 [ ] 框住，不看 Excel 裡任何其他欄位——
程式碼註解特別提到，原本有考慮拿 Excel 的語言欄位（S 欄）來判斷，但
放棄了，因為就算語言欄位標著中文，Excel 裡存的標題文字仍然是英文翻譯，
不是真正拿去 CNKI 搜尋用得上的中文原文篇名，所以乾脆改成完全依賴 DOI
（Excel L 欄）去精確定位文章，不需要用篇名搜尋。

--------------------------------------------------------------
8-3. 一段「查詢方式的演進史」：從直接搜尋到官方 DOI 解析服務
--------------------------------------------------------------

這個檔案開頭的註解，完整記錄了一段「原本的做法行不通，換了另一種做法」
的除錯過程，很值得學習這種思考方式：

  最初的想法：既然有 DOI，直接組一個 CNKI 搜尋網址（搜尋欄位選 DOI、
  貼上 DOI 值）不就好了？

  實測發現的問題：CNKI 的「一框式搜尋」DOI 欄位，比對邏輯其實是抓
  「前綴（prefix）」比對，不是「完全相符」——查一篇文章的 DOI，卻
  跑出一萬七千多筆結果（整本期刊的文章都被撈出來，因為同一本期刊底下
  所有文章的 DOI 通常共用同一段前綴）。CNKI 另外有個「高級檢索」功能
  提供「精確」比對模式，但那個模式常常直接 0 筆結果（可能是索引沒有
  對應到，屬於 CNKI 系統本身的問題）。

  最終解法：改用 CNKI 官方提供的一個「DOI 解析服務」
  （www.chndoi.org），這個服務不需要登入、也不吃 EZproxy 的登入
  session，你只要對它發一個帶 DOI 參數的請求，它會回傳一個「多重解析
  地址選擇頁面」，列出符合這個 DOI 的文章題名/作者資訊，供你核對是不是
  真的找對文章，並提供兩個連結：「境內」（中國大陸境內存取用）跟
  「境外」（海外存取用）——這個專案要的當然是「境外」那個。

  這整段的教訓是：**當一個「看起來理所當然」的做法（直接用搜尋框查
  DOI）實測後發現行不通，不要一直在原本的路上打轉硬凹，去找這個服務
  本身有沒有提供「更精確、更適合這個用途」的另一條路（官方 DOI 解析
  服務）**——這在跟外部系統整合的時候是常態，外部系統的行為常常跟
  文件描述的、或直覺以為的不一樣，需要願意繞路去找替代方案。

--------------------------------------------------------------
8-4. 拿到「境外連結」之後，還要轉一手才能用
--------------------------------------------------------------

chndoi.org 解析出來的「境外」連結，是 CNKI 的原始網域
（link.oversea.cnki.net），不能直接拿去導航過去——這裡又是一個跟階段
3 的 EZproxy 概念完全相同的坑：CNKI 認證機構授權的方式，看的是「這個
請求是不是真的透過 CMU 這台 EZproxy 伺服器轉發過來的」，不是看你瀏覽器
裡存的 cookie；如果直接連到原始網域，CNKI 會把你當成一般訪客（沒有
任何機構授權），導向的是 CNKI 自己的帳號登入頁（不是 CMU 的登入頁，
使用者會看得一頭霧水）。

所以要用階段 3-1 提過的同一套轉換規則（toEzproxyCnkiUrl()，把網域裡
的 `.` 換成 `-`、接上 `.autorpa.cmu.edu.tw:8443`），把這個「境外」
連結轉成代理過的網址，再開分頁導航過去——這個代理連結本身會自動再
跳轉到真正的文章頁，因為前面已經先訪問過 CNKI_PORTAL_URL（中國知網
海外版入口）建立過 EZproxy 對這個資源的 session，這時候就能沿用，
直接看到完整文章內容不需要再登入一次。

--------------------------------------------------------------
8-5. 為什麼下載一定要「真的點擊」按鈕，不能直接組網址
--------------------------------------------------------------

到了文章頁，這個流程刻意選擇「用程式碼模擬真的點擊頁面上的下載按鈕」
（先點 `a.btn-download-logo` 展開下拉選單，再點選單裡的 `a#pdfDown`
連結），而不是像其他出版商那樣，試圖直接組出 PDF 檔案的網址去下載——
原因是 CNKI 的下載端點會檢查 HTTP 請求的 Referer 表頭（代表「這個
請求是從哪個網頁點過來的」），如果不是真的從自己的文章頁點擊連結過去
觸發的請求，就會回傳一個「來源應用不正確」的假錯誤頁（外觀可能還是
HTML，內容卻不是真正的 PDF）。

Referer 這種表頭是瀏覽器自動夾帶的，網頁裡的 JavaScript 沒辦法直接
偽造或覆寫它——唯一能讓它「看起來真的是從這個頁面點過去」的辦法，
就是真的觸發一次瀏覽器原生的點擊/導航動作，讓瀏覽器自己照正常規則
夾帶 Referer。這跟階段 4 提過 Ovid 網站需要靠「真的分頁導航」才能拿到
真檔案，是同一類問題的不同案例——**只要伺服器端會檢查瀏覽器自動夾帶、
JS 沒辦法竄改的表頭，就沒有繞過去的捷徑，只能老老實實觸發一次真正的
瀏覽器動作**。

點擊觸發下載後，用 `chrome.downloads.onDeterminingFilename` 這個
事件監聽器攔截這次原生下載，改成存到呼叫端指定的資料夾/檔名（這個
攔截技巧在階段 2 提過的「檔名登記表」那段有稍微帶到，這裡是它實際
被用到的一個場景）。

任何一步失敗（缺 DOI、chndoi.org 解析不到境外連結、逾時、下載內容
其實是假的錯誤頁）都不會讓這篇論文直接判定失敗，而是把失敗原因記下來，
交還給呼叫端（background.js 的 getPdfUrlWithFallback()）去 fallback
回原本的 PubMed 標準流程再試一次——這也是這個專案一貫的設計原則：
多準備幾條路，一條走不通換下一條，而不是走不通就直接放棄。

========================================================================
階段 9：popup.js 前端狀態管理與訊息通訊（最後一階段）
========================================================================

--------------------------------------------------------------
9-1. 為什麼這個「popup」不是傳統的 Chrome popup？
--------------------------------------------------------------

一般 Chrome 擴充功能常見的做法，是點擴充功能圖示，跳出一個固定在圖示
旁邊的小視窗，你點一下畫面其他地方，這個小視窗就自動關閉——那種叫
Chrome 的 "action popup"，是瀏覽器內建管理生命週期的一種特殊 UI。
這個專案沒有用那種：background.js 裡的 `chrome.action.onClicked`
監聽器（第 51-78 行）自己手動呼叫 `chrome.windows.create()` 開一個
**獨立的、正常的瀏覽器視窗**（type: "popup"，只是這個 type 值是在講
「這個視窗沒有網址列、書籤列這些一般分頁視窗的介面元素」，跟前面說的
那種「點旁邊就自動關掉」的 action popup 完全是兩回事），載入
popup.html 當內容。

為什麼要這樣做？因為這個介面需要長時間開著監看下載進度、需要能跟
使用者互動處理登入/驗證碼/人機驗證這些需要使用者留在畫面上操作的
情境——如果用那種「點旁邊就自動關閉」的傳統 popup，使用者稍微點一下
別的地方（例如去看一下某個分頁在幹嘛），整個操作介面就消失了，非常
不適合這種長時間監看的使用情境。獨立視窗就沒有這個問題，行為跟一般
應用程式視窗一樣。

--------------------------------------------------------------
9-2. 核心概念：popup.js 隨時可能「整個重新開始」，但下載不受影響
--------------------------------------------------------------

這是理解這一整塊訊息通訊設計最關鍵的一件事：**popup.js 執行的環境
（那個獨立視窗）是完全可以被使用者關掉的**——使用者關掉這個視窗、
或者不小心點到重新整理，popup.js 裡所有的 JavaScript 變數會全部
歸零、重新從頭執行一次（跟一般網頁被重新整理是一樣的行為）。但整個
下載任務的「大腦」，也就是階段 2 講的那整套 worker/佇列邏輯，是跑在
background.js（Service Worker）裡的，它**不會**因為 popup 視窗被關掉
就跟著停止——這兩者是完全獨立的執行環境，popup 視窗只是一個「拿來看
進度、跟使用者互動」的顯示器，不是下載任務本身。

這帶來一個實際上很重要的設計後果：popup.js 每次「重新開始」（不管是
第一次開啟、還是使用者關掉又重新點開），都需要一套辦法去「追上」
background.js 那邊目前真正的進度到底跑到哪——這就是 GET_STATE /
getPublicState() 這組機制的用途。

--------------------------------------------------------------
9-3. GET_STATE：popup 重新連線時怎麼「追上進度」
--------------------------------------------------------------

popup.js 一啟動（第 205 行），第一件事就是送一則 `{action: "GET_STATE"}`
訊息給 background.js，background.js 收到後（階段 2 提過的
chrome.runtime.onMessage 那個大 switch），呼叫 getPublicState()（第
636 行）——這個函式把 G 這個內部狀態物件（前面提過它裝了非常多內部
細節，例如登入鎖、cookie 清理旗標這些 popup 完全不需要知道的東西）
篩選、整理成一份「popup 真正需要知道的精簡版本」回傳：目前跑到第幾篇、
成功幾篇、最近 100 條 log、目前是不是在等使用者輸入帳密/驗證碼/處理
人機驗證...等等。

popup.js 拿到這份狀態後，一次把整個畫面「補」成正確的樣子（第 205-243
行）：如果 s.running 是 true，就把開始按鈕設成不能按、狀態文字改成
「下載中」；如果 s.waitingLogin 是 true，就顯示登入表單；如果
s.verifyPending 是 true，就顯示人機驗證的提示區塊......這一段程式碼
本質上是在做「把畫面重建成跟 background.js 現在的真實狀態一致」這件
事，跟你重新整理一個網頁、網頁要重新去伺服器問一次「我現在應該長
什麼樣子」是同一種概念。

這也是為什麼你可以把 popup 視窗關掉，過一陣子重新點開擴充功能圖示，
畫面會直接顯示「目前正在下載第幾篇」，而不是回到一片空白——因為
background.js 這個大腦從頭到尾沒有停過，popup 只是重新問了它一次
「現在狀況如何」。

--------------------------------------------------------------
9-4. GET_STATE 之後：background.js 主動「推播」後續更新
--------------------------------------------------------------

GET_STATE 只解決「popup 剛連上線那一瞬間」要怎麼補齊畫面，但下載
持續在跑，畫面要跟著即時更新——這部分不是 popup 每隔幾秒鐘再去問一次
（那種做法叫「輪詢 polling」），而是反過來：background.js 主動把每個
事件都「推播」出去，popup.js 只要被動接收、更新畫面就好。

這也是階段 2 就出現過、當時先跳過細節的 addLog()、notifyProgress()、
notifyWorkers() 這些函式真正的用途：background.js 裡任何地方只要
呼叫 `chrome.runtime.sendMessage({action: "LOG", ...})` 這種寫法，
如果剛好有 popup 視窗開著、而且它的 onMessage 監聽器正在運作，這則
訊息就會被送到、觸發 popup.js 那邊的處理邏輯。popup.js 的接收端
（第 249 行開始）是一長串 `if (msg.action === "XXX") { ... }`，每種
action 對應一段更新畫面的邏輯：

  LOG           → appendLog()：在 log 區塊加一行文字
  THREAD_LOG    → appendThreadLog()：加一行技術細節紀錄
  PROGRESS      → updateStats() + updateProgress()：更新統計數字跟進度條
  RESULT_UPDATE → 更新這一篇的結果、重新渲染進度表格
  WORKERS       → updateWorkers()：更新每個 worker 目前狀態的顯示
  DONE          → 全部結束，恢復按鈕可以按的狀態
  LOGIN_FAILED_STOP → 顯示登入失敗訊息

  （這裡可以跟階段 4 的 FULL_TEXT_PLATFORMS 分派表比較一下：那邊因為
  規則很多、常常要新增，值得收斂成一張表；這裡訊息種類雖然也不少，
  但每種都要接到完全不同的一段 DOM 更新邏輯、彼此差異很大，寫成一串
  if 反而比硬凹成一張表更直接好讀——這也是個小提醒：分派表不是任何
  時候都比較好，工具要挑對地方用。）

有個容易被忽略、但很重要的細節：background.js 這邊送訊息時，幾乎每個
呼叫後面都接著 `.catch(() => {})`（例如 `chrome.runtime.
sendMessage({...}).catch(() => {})`）——這是因為如果**此刻根本沒有
popup 視窗開著**，`chrome.runtime.sendMessage()` 這個呼叫會失敗（回傳
一個被拒絕的 Promise，因為訊息傳出去了、卻沒有任何一端在監聽接收），
但這對 background.js 來說完全不是問題——它不在乎有沒有人在聽，該做
的下載工作照常做，訊息傳不出去就算了，加上 `.catch(() => {})` 純粹
是為了「接住這個必然會發生、但完全不需要處理的失敗」，避免 Chrome
在背景主控台印出一堆沒人在乎的錯誤訊息。這是一種很典型的「發送端
完全不管有沒有接收端在聽」的通訊模式，你可能聽過的說法是
"fire-and-forget"（射後不理）或跟「發布/訂閱（pub/sub）」模式的精神
接近——background.js 只管「發生了什麼事」，不管「現在有誰在乎」。

--------------------------------------------------------------
9-5. 反方向：popup.js 怎麼「命令」background.js 做事
--------------------------------------------------------------

上面講的是 background.js → popup.js 這個方向（狀態/事件通知），反過來
popup.js → background.js 這個方向，則是使用者操作介面觸發的「命令」：
使用者按下開始／暫停／停止按鈕，popup.js 送出對應的
`{action: "START_DOWNLOAD", targets: [...], concurrent: ...}`、
`{action: "PAUSE_DOWNLOAD"}`、`{action: "STOP_DOWNLOAD"}` 這類訊息，
background.js 那個大 switch（階段 2 開頭看過的那段）收到後執行對應的
動作、修改 G 的狀態、視情況呼叫 sendResponse() 回一個結果給 popup（例如
「開始失敗，因為已經有任務在跑」這種立即性的回應，這時候用的是
sendResponse 而不是後續持續推播的 sendMessage）。

這樣一來，整個系統的訊息流向就很清楚了：popup → background 是「使用者
要求做什麼」，background → popup 是「發生了什麼事、現在狀態如何」，
兩個方向各自獨立，互不阻塞——這正是階段 1 一開始就提過的 Message
Passing 概念，繞了一圈，這裡終於看到它在整個系統裡具體撐起了什麼。
