# 人機驗證偵測與滑鼠移動機制說明

給未來的自己／其他 AI／其他人看的技術筆記，說明 2026-07-24 那次修改動了什麼、
為什麼動、還有哪些已知限制。程式碼裡本來就有很細的中文註解解釋每個決策，這份
文件是把散落在 `src/background.js`、`src/location_target/location_target.js`、
`native_host/python_write_love.py`、`src/discord/discord_notifier.js` 裡的
改動串成一個完整故事，方便一次看懂全貌，不用自己東翻西找。

對應的 commit：`f8096f7`（`git log` 找得到完整 diff）。

## 背景：整套人機驗證提醒的架構

1. `background.js` 下載某篇論文時，用 `chrome.scripting.executeScript` 掃描分頁
   DOM，找 Cloudflare Turnstile／reCAPTCHA／hCaptcha／px-captcha 這類驗證挑戰
   元件（選擇器見 `MANUAL_VERIFICATION_CHALLENGE_SELECTOR_DEFAULT`）。
2. 找到候選元件後，`location_target.js` 的 `locateAllTargetElements()` 把每個
   候選的 DOM rect 換算成螢幕絕對座標（`rectToScreenPoint()`，處理視窗位置、
   瀏覽器 UI 佔用高度、devicePixelRatio）。
3. `background.js` 呼叫 Chrome Native Messaging host
   `com.pubmed_downloader.write_love`（實際跑的是
   `native_host/python_write_love.py`），把候選座標當「這裡大概是驗證元件」的
   提示傳過去。
4. Python 端**不盲目相信這個座標**，自己在這個範圍內用多尺度樣板比對
   （OpenCV `matchTemplate`）找出 checkbox 精確位置，用真人錄製軌跡（優先）或
   合成貝茲曲線把 OS 滑鼠移過去（**只移動、不點擊**——這支工具是提醒真人來
   手動處理驗證，不是自動幫真人點掉，`main()` 上面那段 docstring 特別強調
   這件事，之前工作目錄裡也曾經把真的會點擊的 `mouse_event` 那幾行手動註解掉
   過，這個「不自動點擊」的定位要維持住，之後不要加回去）。
5. 疊一個半透明視窗在真實畫面上，藍框標 DOM 量到的候選外框、紅框標比對到的
   checkbox、黃點標滑鼠實際去的點，畫完幾秒後自動關閉、回 ack，`background.js`
   才處理下一個候選。

這套機制原本運作良好，但實際遇到 Elsevier/ScienceDirect 的 Cloudflare 驗證頁時
使用者回報：完全抓不到 iframe/checkbox，甚至系統根本沒告訴使用者「這是驗證
頁」。往下追查出三個問題，逐一修掉。

## 問題 1：判斷「有沒有驗證」的邏輯有好幾套、彼此不一致

`background.js` 裡曾經有**三處**各自獨立判斷「這是不是驗證頁」的地方：

| 函式 | 用途 | 原本的問題 |
|---|---|---|
| `checkPageState()` | 判斷 PubMed 文章頁本身是不是 bot 頁 | 選擇器是舊的一份，沒有 `[id^='cf-chl-widget-']`／`iframe[src*='challenges.cloudflare.com']`，判到 `"bot"` 只會直接判失敗，完全沒接進驗證暫停流程 |
| `tabShowsManualVerification()` | 判斷出版商頁面（ScienceDirect 等）是不是卡在驗證頁 | 用共用選擇器沒錯，但 `document.querySelectorAll` **沒有穿透 shadow root** |
| `locateAllTargetElements()`（`location_target.js`） | 實際去抓候選元件座標 | 唯一有穿透 shadow root 的版本 |

**為什麼 shadow root 很重要**：Cloudflare Turnstile 等挑戰元件常把實際渲染出的
iframe/容器包在 open shadow root 裡再插進 DOM，只查 `document` 這一層直接會漏掉。
`tabShowsManualVerification()` 的判斷結果**直接決定要不要觸發整套暫停+提醒
流程**，這裡漏判比 `locateAllTargetElements()` 漏判嚴重得多——後者只影響定位
準不準，前者漏判會讓使用者完全不知道卡在驗證頁。

**修法**：
- `tabShowsManualVerification()`、`checkPageState()` 都補上跟
  `location_target.js` 的 `deepQuerySelectorAll` 同一套遞迴穿透 shadow root
  的邏輯（三處各自 inline 一份，因為 `chrome.scripting.executeScript` 的
  `func` 是被序列化後單獨在頁面環境執行，沒辦法直接 import 共用函式）。
- `checkPageState()` 改用共用的 `getManualVerificationChallengeSelector()`，
  不再自己維護一份獨立、容易忘記同步更新的清單。
- `checkPageState()` 判到 `"bot"` 時，改成呼叫
  `requestManualVerificationPause()` 走跟出版商頁面一樣的暫停+提醒流程
  （見 `background.js` 裡 `checkPageState` 的呼叫點附近註解），不再直接判失敗。

## 問題 2：完全沒有候選元件時，直接放棄，不做任何掃描

`python_write_love.py` 裡有個開關：

```python
ENABLE_BLIND_FULLSCREEN_SEARCH = False
```

沒有 `dom_region`（background.js 完全沒抓到候選）時，原本**直接回傳 `None`，
一次掃描都不做**——這就是使用者說的「空白視窗」：不是掃描失敗，是根本沒掃。
這個開關被關掉是因為之前試過對「整個虛擬桌面」（`capture_virtual_desktop()`
抓 `sct.monitors[0]`，含其他螢幕、桌面圖示、工作列）做全螢幕模板比對，誤判
太多，準度不夠。

**修法**：新增一個獨立的「視窗範圍盲搜」層，不受 `ENABLE_BLIND_FULLSCREEN_SEARCH`
影響（那個開關代表的「整個虛擬桌面」盲搜維持關閉，風險還是太高）：

- `location_target.js` 新增 `getViewportScreenBounds(tabId)`：沿用
  `rectToScreenPoint()` 同一套換算公式，把 rect 設成「整個 viewport 本身」
  （left/top=0,0、width/height=innerWidth/innerHeight），算出瀏覽器視窗內容區
  的螢幕絕對範圍。
- `background.js` 的 `triggerVerificationHeart()`：完全沒抓到候選元件時，
  呼叫上面這個函式，把視窗範圍當 `windowRegion` 塞進送給 native host 的 payload。
- `python_write_love.py`：把原本 `dom_region` 專用的比對邏輯（先比 checkbox
  樣板、沒中再找 logo 當備援、鎖定附近小範圍再比一次）抽成共用函式
  `_locate_checkbox_in_region()`，`dom_region` 跟新的 `window_region` 都呼叫
  同一套，只是門檻不同（`WINDOW_REGION_MIN_SCORE=0.55`／
  `WINDOW_REGION_LOGO_MIN_SCORE=0.75`，範圍大很多、假陽性風險也高，門檻拉高）。
- 回應多了 `windowRegionUsed` 欄位，`background.js` 的 log 會標「（來自視窗
  範圍盲搜）」，方便事後判斷這次是精準定位還是退到視窗範圍找到的。

**附帶修的一個 bug**：提醒視窗（透明疊層）本身的畫布最大只有
`MARKER_MAX_SIZE=900` px 見方，原本置中的基準是看 `region`——`region` 現在除了
`dom_region`（通常不大）之外也可能是 `window_region`（整個瀏覽器視窗，動輒
1500x900 起跳，遠超過 900）。如果還是拿 `region` 置中，checkbox 真正的位置
很容易落在視窗中心以外，被裁到畫布外面完全看不到（滑鼠確實移動過去了，畫面上
卻沒有任何標記，看起來又是一次「空白提醒視窗」）。改成 `box`（真的比對到的
checkbox 精確範圍）有的話一定優先拿它置中，`region` 只在沒比對到 checkbox 時
才當退路。

## 問題 3：連 HTML 都沒有，沒辦法對症下藥

使用者回報 Elsevier 的驗證頁樣式，但手邊沒有留下實際 HTML，沒辦法針對性調整
選擇器/關鍵字。新增了「疑似驗證頁但抓不到任何已知訊號」時自動存證的機制
（`captureVerificationPageSnapshot()`，`background.js`）：

- `warmUpAntiBotChallenge()`（ScienceDirect/Elsevier 走的路）：連續 3 次輪詢
  都偵測不到任何已知驗證訊號、但也還不是真 PDF 時，存一次。
- `monitorManualVerification()`：判定為驗證頁但 `locateAllTargetElements`
  一個候選都抓不到時（對應「只跳空白視窗」的症狀），第一次嘗試時存一次。

存的內容（`document.documentElement.outerHTML` 截斷 20000 字 + 標題 + 網址）
會透過 `addThreadLog()` 進到 `G.debugRun.threadLogs`，批次結束時一起寫進
`native_host/debug_log/` 的 debug log 檔（`buildDebugLogText()`／
`writeDebugLogFile()`）。**下次再遇到 Elsevier 這個驗證頁，翻最新的 debug log
搜尋「Verification page snapshot」或「no known challenge signal matched」**，
就能拿到實際 HTML，照著調整選擇器。截至這次修改，還沒有拿到真正的樣本，
這是最大的已知未解問題。

## Discord 通知有時候收不到

`discordWebhookPost()`（`discord_notifier.js`）原本單次 `fetch()`，失敗（網路
瞬斷、Discord 429/5xx）只寫進 `addThreadLog`（不會顯示在主 UI），也完全沒有
重試——這就是「有時候收不到」的真正原因，不是 webhook 設定壞掉。

修法：最多重試 2 次；429 時照 Discord 回應帶的 `retry_after` 秒數等待再送，
5xx 用固定短延遲重試，其他 4xx（webhook 網址本身失效/權限問題）直接放棄不重試；
全部重試用盡才真的放棄，這時額外呼叫 `addLog()`，主畫面會看到「⚠ Discord 通知
發送失敗（已重試 2 次仍未成功）」。

**沒修的已知風險**：`G.discordBatch`／`G.discordAllItems` 是純記憶體狀態，如果
MV3 service worker 中途被 Chrome 砍掉重啟會歸零、遺失還沒送出的批次。但那個
情境下整個下載批次也會一起中斷（`G` 整包被 `resetState()` 重置），使用者應該會
明顯感覺到「整批停了」，不會只是悄悄漏一則通知，所以判斷這不是主要原因，暫時
沒動；如果之後真的遇到「整批莫名中斷」，才需要另外做 run 狀態的 persist/resume
（目前完全沒有這個機制，`completedPmids` 之類的 progress 有存 chrome.storage，
但 `G.queue`／`G.workers` 這些跑時狀態沒有）。

## 滑鼠移動速度忽快忽慢、近距離會抖動

`python_write_love.py` 的滑鼠移動有兩條路：優先重播真人錄製軌跡
（`replay_user_trace_template()`，讀
`真人點擊資料收集/mouse_recording/*_checkbox_100.json`），沒有錄製檔或用不上
才退回合成貝茲曲線（`smooth_move_mouse_to()` 自己的 `MOVE_PATTERNS`）。

**兩個問題疊在一起**：

1. **總耗時縮放範圍太窄**：兩條路原本都用「`clamp(實際距離 / 參考距離, 窄範圍)`」
   決定總耗時——`replay_user_trace_template` 是 `clamp(.., 0.60, 1.45)`，
   `smooth_move_mouse_to` 是 `clamp(.., 0.70, 1.12)`。但滑鼠起始位置千變萬化
   （尤其現在有了 window_region 盲搜，目標可能落在整個瀏覽器視窗任何角落），
   實際距離常常差到 5-10 倍以上，總耗時卻只能跟著變這麼窄的範圍：近距離被迫
   拖慢、遠距離跟不上只能用飛的——這是系統性的，不是隨機。改成開根號縮放
   （距離變 4 倍、時間約變 2 倍，比較接近真人「距離越遠移動越快但不是等比例
   快」的直覺）並大幅拉寬 clamp 範圍（`replay_user_trace_template`：
   0.45~2.3，總耗時上限 0.28~3.2 秒；`smooth_move_mouse_to`：0.5~2.3）。

2. **軌跡樣板挑選太隨機，短距離會抖動**：`replay_user_trace_template()` 原本
   `random.choice(templates)` 純隨機挑一筆錄製軌跡，不管那筆原本錄製時走了多
   遠。軌跡裡的垂直抖動量（`v`）存成「原始錄製距離的比例」，套用時乘上**這次
   實際距離**還原成絕對座標——隨機挑到一筆原本是長距離（例如 400px）錄的軌跡，
   卻套在這次只有 20-30px 的短距離移動上，抖動比例會被壓縮硬套進小很多的空間，
   變成密集、不成比例的鋸齒晃動，看起來又慢又抖。改成優先挑「原始錄製距離」
   跟這次實際距離相近的一批（最接近的前 1/3）再隨機選一筆；如果連最接近的
   樣板距離都差超過 3.5 倍或不到 0.3 倍（代表收集到的錄製檔剛好沒有這種距離
   量級的樣本），直接放棄重播、回傳 `None`，退回 `smooth_move_mouse_to()` 的
   合成貝茲曲線——那條路徑的抖動量是固定的小像素數，不隨距離縮放，短距離
   移動反而更平滑。

## 已知還沒解決 / 之後可以繼續做的

- **Elsevier 驗證頁的實際 HTML 樣本還沒拿到**：上面「問題 3」的自動存證機制
  已經上線，但截至這次修改還沒有實例。使用者下次遇到 Elsevier 驗證頁卡住時，
  跑完之後翻 `native_host/debug_log/` 最新那個檔案，把 HTML 貼出來就能繼續往
  下調整選擇器（很可能是 Cloudflare Turnstile Enterprise 用了自訂網域，
  iframe `src` 不含 `challenges.cloudflare.com`/`turnstile` 字樣，導致目前所有
  以 `iframe[src*=...]` 為主的選擇器都失效——這是目前最大的懷疑方向，但沒有
  實際 HTML 之前只是猜測）。
- **Discord 批次狀態沒有 persist/resume**：見上面「Discord 通知有時候收不到」
  最後一段，如果之後真的觀察到整批下載中途莫名消失（不是只有 Discord 沒收到），
  要往這個方向查。
- **`checkPageState()` 判到 bot 之後接進驗證暫停流程**這個改動，是照著出版商
  頁面的既有模式做的，但這個情境（PubMed 頁面本身被擋）目前還沒有實際案例
  驗證過，理論上應該通、但沒有真實驗證資料。
